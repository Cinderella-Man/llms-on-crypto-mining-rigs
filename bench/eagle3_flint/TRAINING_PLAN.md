# Training an EAGLE-3 head for Flint

This is the plan for the case where the [one-hour check](README.md) says **GO**. It trains a one-layer EAGLE-3 drafter
for [Flint](https://huggingface.co/RecursiveSI/flint) with exactly the shape that was timed on the rig, on a single
machine without cloud GPUs:

| Quant machine | |
|---|---|
| GPUs | 3 × RTX 3090 24 GB, 2 × V100 32 GB (no BF16), 2 × RTX 3080 10 / 12 GB; 158 GB in total |
| Interconnect | PCIe x1–x8 per card, no NVLink, no peer-to-peer |
| Host | Ryzen 9 5900X (24 threads), 94 GB RAM, Docker |
| Model files | Flint BF16 (80 GB); a Q8_0 GGUF (42.3 GB, [unsloth/flint-GGUF](https://huggingface.co/unsloth/flint-GGUF) or converted from the BF16 files) |

**In one paragraph.** Flint answers ~60,000 prompts with llama-server on its Q8_0 GGUF (two copies, several slots
each). A small llama.cpp tool replays those token sequences through the same GGUF and saves, for every token, the
inputs of Flint's layers 2, 24 and 46 and its final hidden state, the features EAGLE-3 learns from. SpecForge, in its
offline mode, trains the head from those files on the three RTX 3090s. The checkpoint converts to GGUF with the same
converter command as the random heads in [README.md](README.md) and runs on the rig with `--spec-type draft-eagle3`.
A 20,000-prompt pilot comes first and has its own go/no-go gate on the rig.

| | Pilot | Full run |
|---|---|---|
| Prompts regenerated by Flint | 20,000 | 60,000 (the pilot's included) |
| Tokens (prompt + response) | ~30 M | ~90 M |
| Feature storage (BF16, 16.4 KB per token) | ~0.5 TB | ~1.5 TB |
| GPU-hours (estimate) | 35–56 | 105–180 more |
| Wall-clock | ~2 days | ~3–4 more days |

## 1. Software stack

### What was considered

| Option | Verdict | Why |
|---|---|---|
| **SpecForge, offline mode** ([repo](https://github.com/sgl-project/SpecForge)) | **Use for training** | Supports EAGLE-3 with a 32k draft vocabulary, training-time test, and an "offline colocated" mode in which the trainer only reads precomputed feature files (`examples/configs/offline/colocated/`). Its checkpoints are the `LlamaForCausalLMEagle3` format that llama.cpp's converter names as supported. |
| SpecForge, online mode | Not possible | Since commit `7d1fbf0` (2026-07-14, "cut over to server-only algorithm runtime") the target runs only inside an SGLang server. SGLang has no Flint support yet ([PR #45624](https://github.com/sgl-project/sglang/pull/45624), open since 2026-10-21), and Flint's own SGLang kit needs one GPU with ≥ 141 GB per replica ([sglang/README.md in the model repo](https://huggingface.co/RecursiveSI/flint/blob/main/sglang/README.md), 2026-10-21). |
| SpecForge's former Hugging Face backend | Not possible | Removed in the same commit; it also loaded the whole target on one GPU per rank. |
| [EAGLE repo](https://github.com/SafeAILab/EAGLE) (`eagle/traineagle3/`, last commit `cb7e084`, 2026-02-19) | Reference only | Runs its own Llama implementation of the target in-process; its README now points to SpecForge. Its hyperparameters are listed in section 4. |
| [vLLM speculators](https://github.com/vllm-project/speculators) v0.9.0 (2026-10-19) | Not possible today | Takes hidden states from a vLLM server. vLLM's Flint support ([PR #62938](https://github.com/vllm-project/vllm/pull/62938), merged 2026-10-22, not yet released) doesn't implement the EAGLE-3 hidden-state interface, and speculators requires transformers ≤ 5.19, which has no Flint. |
| transformers' native Flint ([PR #49824](https://github.com/huggingface/transformers/pull/49824), merged 2026-10-21) for features | Not practical here | Not in any release yet (latest v5.20.2, 2026-10-19). Attention runs in the `eager` implementation (SDPA can't apply the attention sinks), the grouped-GEMM expert path needs compute capability 8.0+, BF16 weights (80 GB) exceed the three RTX 3090s (72 GB), and the V100s can't compute in BF16. |
| **llama.cpp's hidden-state API** (`llama_set_embeddings_layer_inp`, `src/llama-ext.h`) for features | **Use for features and responses** | Already used by llama.cpp's own EAGLE-3 drafting, works for Flint (its graph records every layer's input), runs on all seven GPUs including the V100s, and produces the features from a GGUF of the same model and engine that the rig serves. |

| Component | Version | Notes |
|---|---|---|

Run each part in its own Docker container: a CUDA 12.9 image for llama.cpp, and a PyTorch/CUDA 12 image with SpecForge
installed from the pinned commit. Training runs on the RTX 3090s only: SpecForge's training loop uses BF16 parameters
(FSDP mixed precision and its `BF16Optimizer`), which the V100s can't compute.

### Feature-layer convention

llama.cpp reads the **inputs** of target layers 2, 24 and 46 (its default `[2, L/2, L−3]` for L = 49). SpecForge's
default `[1, L/2−1, L−4]` = `[1, 23, 45]` counts layer **outputs**, which are the same three tensors. Because the
features here come from llama.cpp, the convention only has to hold in two places: the dump tool must save the inputs
of layers 2, 24 and 46, and the draft config must not set `eagle_aux_hidden_state_layer_ids` (llama.cpp's converter
then records [2, 24, 46]).

## 2. Data: prompts and Flint's responses

### Prompt sets

EAGLE-3 learns to predict *Flint's* next tokens, so every training response must be generated by Flint; only the
prompts come from public data sets. Flint is tuned for agentic coding, so the mix weights code and tool calls more
than the classic ShareGPT + UltraChat recipe.

### Regeneration with llama-server

Two llama-server copies of the Q8_0 GGUF, each with many parallel slots (continuous batching):

```bash
# copy A: the three RTX 3090s (72 GB for 42.3 GB of weights + KV cache)
CUDA_VISIBLE_DEVICES=<3090s> llama-server -m flint-Q8_0.gguf -ngl 99 -fa on -np 48 -c 196608 -b 2048 -ub 512 \
    --host 127.0.0.1 --port 8001
# copy B: the two V100s (64 GB)
CUDA_VISIBLE_DEVICES=<V100s> llama-server -m flint-Q8_0.gguf -ngl 99 -fa on -np 32 -c 131072 -b 2048 -ub 512 \
    --host 127.0.0.1 --port 8002
```

`-c` is split between the slots: 4,096 tokens each, enough for a prompt plus a 2,048-token response. Flint's KV cache
is small (~28 KiB per token in the 14 full-attention layers plus a 513-token window in the others), so 48 slots
need ~7 GB.

A client script (~150 lines of Python, to be written) sends the prompts to both servers in parallel and stores exact
token ids, so nothing is re-tokenized later:

1. `POST /apply-template` with the messages (and `tools`): the prompt text in Flint's own chat template, including its
   tool format.
2. `POST /tokenize` (`parse_special: true`): the prompt's token ids.
3. `POST /completion` with the prompt, `n_predict: 2048`, Flint's recommended sampling from its
   `generation_config.json` (temperature 1.0, top-p 0.95, top-k 20) and `return_tokens: true`: the response's token
   ids, including its `<think>` block.
4. Append `{"input_ids": prompt + response, "loss_mask": [0]*len(prompt) + [1]*len(response)}` to a JSONL file;
   resume from the last written line after an interruption.

Responses cut at 2,048 tokens are kept; a drafter learns from every position. Sampling at Flint's deployment
temperature makes the drafter learn the distribution it will meet; SpecForge's own data bundle used temperature 0.8
([SpecForge paper](https://arxiv.org/abs/2603.18567), 2026-03-19).

**Throughput (estimate, measure first).** At 48 parallel requests each MoE layer touches ~68 % of Flint's 256 experts
per step, so a step reads ~29 GB, about 45 ms across three RTX 3090s: ~1.0–1.3k tokens/s for copy A and ~0.7–1.1k for
copy B, together ~1.6–2.4k tokens/s. Run the client for 10 minutes on 500 prompts before starting and adjust `-np`.
With ~1,200 response tokens on average: pilot (24 M response tokens) 3–4 hours, full set (72 M) 8–13 hours.

### Draft vocabulary

Count how often each token id occurs in the responses (`loss_mask == 1`), take the 32,000 most frequent, and make
sure Flint's structural control tokens (`<think>`, `</think>`, `<tool_call>`, `<arg_key>`, `<arg_value>` and their
closing tags) are in the set, replacing the least frequent tokens if needed. Write `d2t` (draft index → target id minus draft index, int64) and `t2d` (boolean over the 150,144
target ids) in the format of SpecForge's `generate_vocab_mapping_file()` (`specforge/data/preprocessing.py`) and point
`model.vocab_mapping_path` at it. Record the coverage (share of response tokens inside the 32k set); 97–99 % is
typical, and a lower figure argues for 64k.

## 3. Features

### The dump tool

A small C++ program against llama.cpp `d77256999` (~200 lines, to be written; it uses the same calls as
`common/speculative.cpp`'s EAGLE-3 code):

1. Load the Q8_0 GGUF across the GPUs of one copy, `n_ctx` 4096, `n_batch` 4096, `n_ubatch` 512.
2. Enable `llama_set_embeddings_layer_inp(ctx, l, true)` for l = 2, 24, 46 and `llama_set_embeddings(ctx, true)`
   (Flint's embeddings output is its final hidden state after the output norm, `t_embd` in `src/models/flint.cpp`).
3. Per sample: clear the memory, decode the whole token sequence as one batch with every position marked as output,
   read `llama_get_embeddings_layer_inp()` for the three layers and `llama_get_embeddings()` (n_tokens × 2048 floats
   each), convert to BF16 and append to a shard file with an index.
4. A Python packer turns the shards into SpecForge's offline EAGLE-3 records, one `.ckpt` per sample with `input_ids`,
   `loss_mask`, `hidden_state` (the final hidden state) and `aux_hidden_state` (the three layers concatenated, 6,144
   values per token). Copy the exact tensor shapes from a record that SpecForge's own
   `scripts/prepare_hidden_states.py` writes for a small model such as Qwen3-0.6B.

Marking every position as output also makes llama.cpp copy 150,144 logits per token to the host (600 KB); with 512-token
micro-batches that is ~300 MB per micro-batch. Put the card holding Flint's output layer (the last in the split) in
the fastest PCIe slot.

**Check before the full dump:** multiply 1,000 saved final hidden states by Flint's BF16 `lm_head` and compare the
arg-max with the next token in the sequence. On temperature-1 responses agreement should be high (most sampled tokens
are the arg-max); near-random agreement means an off-by-one or layout error.

**Throughput (estimate).** Prompt processing of Flint Q8_0 is compute-bound at ~5 GFLOP per token: ~2–4k tokens/s
per copy, 3–6k tokens/s for both copies. Pilot (30 M tokens) 1.5–3 hours; full set (90 M) 4–8 hours.

### Storage

Per token: 3 × 2048 × 2 bytes (aux) + 2048 × 2 bytes (final) + ids and mask ≈ **16.4 KB**. Pilot ~0.5 TB, full set
~1.5 TB. If the disk can't hold the full set, dump and train in two halves, or keep the dump running on the V100 pair
while the RTX 3090s train and delete each shard once every epoch has read it (re-dumping per epoch costs ~4–8 hours on
the V100 pair alone).

entries regenerated by the target; no training hours given);
[EAGLE `ds_config.json`](https://github.com/SafeAILab/EAGLE/blob/cb7e0841fe0c206c6ed74a197ad5e2a1f13f5a2b/eagle/traineagle3/ds_config.json)

conversations at lr 1e-4; with ~60k samples more epochs are needed, and held-out acceptance decides when to stop.

**Accumulation 8** because there is no peer-to-peer and some cards sit in x1 slots: an all-reduce of the head's
145 M parameters moves ~290 MB through host memory, which would dominate a one-sample step.

### Configuration

An offline colocated recipe modelled on `qwen3.5-35b-a3b-eagle3.yaml`:

```yaml
model:
  target_model_path: /models/flint-bf16          # Flint's HF folder; only config, embed_tokens and lm_head are read
  draft_model_config: /work/flint-eagle3/config.json   # from make_random_head.py --draft-vocab 32000
  target_backend: sglang                          # required by the schema; not started in offline mode
  embedding_key: model.embed_tokens.weight        # check the names in model.safetensors.index.json
  lm_head_key: lm_head.weight
  vocab_mapping_path: /work/vocab_mapping_32k.pt
  torch_dtype: bfloat16
data:
  hidden_states_path: /data/flint-features
  max_length: 2048
training:
  strategy: eagle3
  num_epochs: 3
  batch_size: 1
  accumulation_steps: 8
  learning_rate: 0.0001
  max_grad_norm: 0.5
  ttt_length: 7
  attention_backend: flex_attention
deployment:
  mode: local_colocated
  trainer: {nnodes: 1, nproc_per_node: 3}
```

**Plumbing test first (2–3 hours, on 100 samples):** SpecForge reads the target's config through `load_target_config`,
which falls back to the raw `config.json` when transformers 5.12.1 doesn't know `model_type: flint`, and loads only
the embedding and LM-head tensors from the safetensors files. If either step still fails, point
`target_model_path` at a stub folder: a Llama-type `config.json` with Flint's sizes (hidden 2048, vocab 150,144,
49 layers) and one safetensors file holding only `model.embed_tokens.weight` and `lm_head.weight` (2 × 615 MB in
BF16), copied from Flint's shards.

### Compute

One sample position costs ~6.7 GFLOP per training pass (forward and backward of a 145 M-parameter head over 7
training-time-test steps, plus the frozen 150,144-row target head for the labels). At 8–14 TFLOPS sustained per RTX
3090 in BF16 (estimate):

- pilot, 30 M tokens × 3 epochs: 12–21 GPU-hours, **4–7 hours** on three RTX 3090s;
- full, 90 M tokens × 5 epochs: 60–105 GPU-hours, **20–35 hours**.

Memory per RTX 3090 at 2,048 tokens: ~2 GB of head weights, master copy and Adam state, ~1.2 GB of frozen embedding
and LM head, ~2.5 GB of logits over 7 steps, plus activations: well under 24 GB. A 12 GB RTX 3080 can run a separate
small ablation (TTT 5, 2,048 tokens); the 10 GB card can't.

## 5. Export and rig test

```bash
# SpecForge checkpoint (config.json + model.safetensors, LlamaForCausalLMEagle3) -> GGUF, as for the random heads
python <llama.cpp>/convert_hf_to_gguf.py <checkpoint> --target-model-dir flint-meta --outtype q8_0 \
    --outfile flint-eagle3-pilot-Q8_0.gguf
```

Check the converter log: architecture `eagle3`, target layers [2, 24, 46], a 32,000-entry `d2t`. On the rig:

```bash
ssh rig "MODEL=<flint gguf> TAG=eagle3_pilot SERVER_ARGS='-c 262144 -b 512 -ub 128 -bs \
    -md /mnt/models/eagle3/flint-eagle3-pilot-Q8_0.gguf --spec-type draft-eagle3 --spec-draft-n-max 3 -devd CUDA8 -ngld 99' \
    bash -s" < scripts/server_bench.sh
```

Measure k = 1–4 at temperature 0 (the four `server_bench.sh` prompts), the same at temperature 1.0, and one replayed
agent session with tools. Record τ (mean tokens per round, from the server's "draft acceptance … mean len" line) and
tokens/s against plain `-bs` serving.

**Pilot gate:** continue to the full run if τ(k = 3) ≥ 2.1 at temperature 0 **or** the measured speed-up at the best
k is ≥ 1.25×. Three times the data should add something like 5–15 % to the acceptance length (estimate), not more, so
a pilot below τ 1.8 means the full run won't reach the README's targets either; look for a data or feature bug before
spending more GPU time.

5. **Days 5–6.** Training finishes; convert, test on the rig (k = 1–4, temperatures 0 and 1, agent replay), write up

## 7. Risks

- **Quantized features.** The head trains on features from the Q8_0 GGUF but runs on the rig's 4-bit file (makers'
  Q4_1 or UD-mirror). The difference is small next to the training noise; if acceptance on the rig falls well short of
  the pilot's held-out acceptance, dump the features from the served file instead (the dump tool takes any GGUF).
- **Temperature.** Published acceptance figures are mostly greedy. At Flint's temperature 1.0, greedy drafts match the
  sampled token less often; `--spec-draft-sampling probabilistic` (rejection sampling) recovers part of that. Measure
  both on the rig.
- **Long contexts.** The head trains on ≤ 4,096-token samples and its own attention uses RoPE; agent sessions reach
  tens of thousands of tokens. Measure acceptance on a long replayed session before relying on it there.
- **Tool calls.** llama-server turns backend sampling off for requests with tools, which costs ~3 ms per verified
  token on the rig (see [README.md](README.md)); the speed-up for agent traffic is lower than for plain chat.
- **SpecForge moves fast.** Its offline path changed several times in 2026; stay on the pinned commit.
