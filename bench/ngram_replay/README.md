# Replaying n-gram drafters on Flint's own output (Q64)

Which draft-model-free speculative decoding pays for Flint on the P106 rig, and for which kind of work? Flint routes
every verified token to 6 of 256 experts with little locality ([Q51](../expert_overlap/README.md)), so a verify step of
n tokens costs a lot, and only drafts that are almost always accepted pay. The cheapest drafters copy from the context.
This replays every n-gram drafter in llama.cpp, and the copy-gated `ngram-copy` drafter designed for Q53
([speculation plumbing](../../docs/research/notes/speculation_plumbing.md) section 5), on transcripts Flint generated
itself, with exact acceptance, and turns the step counts into speed-ups with a verify-cost table (registry row Q64 in
[quants/experiments.md](../../quants/experiments.md)). [pipeline_sim.py](pipeline_sim.py) replays the same transcripts
through a model of pipelined speculation, where no batched verify step exists (Q87).

**Result, batched verification.** At the verify cost measured on the rig, only 2-token drafts pay. `ngram-copy` limited to 2-token drafts gives
1.03× overall and 1.26× on file rewrites, the level of a perfect copy drafter at that width. Q53's 7-token blocks and
every llama.cpp drafter setting lose (0.54–0.97× overall). Blocks of 31–63 tokens would give 2.1–2.7× on file rewrites
only if a verify of 16–64 tokens costs close to the prompt-processing rate per token, which is not measured yet.

**Result, pipelined speculation (simulated).** When guesses enter the first card while later cards still finish the
previous token, each an ordinary one-token step, n-gram guesses give 1.34× overall and 4.0× on file rewrites on six
cards (50 and 151 tokens/s against 37.3), 1.41× and 7.3× on nine cards with a lighter last card, without any training.
A trained one-token drafter needs a per-token acceptance of ~0.4 for 1.5× and ~0.6 for 2×; behind the copy lookup,
p = 0.7 gives 2.3–2.9×. Guessing fresh text from 1–8-token continuation counts (the request's own, plus a table of
other outputs) lifts the n-gram result to 1.44× on six cards and 1.54× on nine (Q96). Gumbel-coupled sampling adds
nothing to those guessers but lifts a near-Flint drafter's acceptance from at most 0.90 towards 1.

## Method

- **Data.** Q51's transcripts ([expert_overlap](../expert_overlap/README.md)): 38 prompts (10 chat, 10 code writing,
  8 whole-file edits of this repository's scripts, 10 agent turns with four coding tools), generated by Unsloth's Flint
  Q8_0 at its default sampling (temperature 1.0, top-k 20, top-p 0.95, min-p 0.05), up to 3,072 tokens each, with exact
  prompt and output token ids. 65,520 tokens come from decode steps (the first token of each answer comes from the
  prompt pass). Flint's own tokens split each output into reasoning (`<think>` … `</think>`), tool calls
  (`<tool_call>` … `</tool_call>`) and answer text.
- **Replay.** [replay.py](replay.py) steps through each output as llama-server does: at every step the drafter gets
  the tokens in the KV cache and the last sampled token, and the draft is cut to the room the server allows (context
  and `n_predict`). The step keeps the longest prefix of the draft that equals what Flint generated next and yields
  that many tokens plus one. A drafter hears the accepted count only after a non-empty draft, as in the server.
- **Why the acceptance is exact.** The server verifies n-gram drafts by sample-and-match: it samples each position from
  the target and keeps a draft token while the sample equals it. The transcripts are samples from the target at the same
  settings, so the count of kept tokens on this output is the count the server would see on the same output.
- **Drafters.** Line-by-line Python ports of the llama.cpp fork's code (branch `pascal-p106`, upstream `d77256999`):
  `ngram-simple`, `ngram-map-k` and `ngram-map-k4v` (`common/ngram-map.cpp`, hash collisions included), `ngram-mod`
  (`common/ngram-mod.cpp` and its driver in `common/speculative.cpp`), `ngram-cache` without cache files
  (`common/ngram-cache.cpp`, at most 8 tokens). [fork_check.sh](fork_check.sh) compiles the fork's three source files
  unchanged with stub headers, drives them with [fork_check.cpp](fork_check.cpp), and compares every step: all 15
  llama.cpp settings below draft the same lengths and accept the same counts at every one of their 45,000–62,000 steps.
  `ngram-mod` shares its table across requests in the server, and `ngram-cache` keeps its counts; here every request
  starts empty, as on a freshly started server.
- **`ngram-copy`** follows Q53's design: the longest match of the context's suffix, 6 to 12 tokens, newest on ties,
  allowed to overlap the suffix (it then continues periodically); 2 drafted tokens per match; 7 after two fully
  accepted steps in a row, while the match has 7 tokens of continuation or is periodic; the long state is held through
  2 missed steps. The sweep varies one parameter at a time. **Tiers** `2/7/15/31` is a variant: the controller climbs
  one tier after every two fully accepted steps and falls back to 2 tokens as the long state does.
- **Copy structure**, independent of any drafter: a greedy longest-previous-match parse of each output against its
  prompt and its own earlier output (sources may overlap the copy). Tokens inside matches of at least 8 tokens count as
  copied; back-to-back copies form a copy run.
- **Bounds.** "Oracle copy" sees the output and drafts exactly the rest of the current copy (≥ 8 tokens), capped at k,
  so it is always accepted and never drafts fresh text. "After 6" waits until 6 tokens of the copy have been generated,
  as any drafter that needs a 6-token key must.

### Cost model

Speed-up = (decode steps without drafting) / (Σ over steps of v(width) + graph costs), where v(n) is the time of a
decode step that verifies n tokens, in T1 (one plain decode step).

**Measured on the rig** (Q19 stage 1, 2026-10-23): the S4-L0 mix on six cards, fork `eeaa59660`, llama-server with
backend sampling (`-bs`) and synthetic full acceptance (the synth part of
[verify_cost.sh](../eagle3_flint/verify_cost.sh): `ngram-simple` drafts with size-n 1 and `--spec-synth-len`). These are
real server steps, so CUDA graph re-captures and the whole verify path are included.

| Mean verify width | 1 | 2.90 | 4.05 |
|---|---|---|---|
| Step time | 25.9 ms (38.6 tokens/s) | 57.7 ms | 92.1 ms |
| v, T1 | 1 | 2.23 | 3.56 |

- The widths are the mean verify lengths of runs set to 3 and 5 tokens.
- llama-bench gives upper bounds for single widths: prompt steps without CUDA graphs take 163.6, 170.0, 207.6 and
  212.1 ms for 5, 6, 7 and 8 tokens. Its 1-token prompt step takes 57.0 ms against 30.8 ms per generated token, so a
  prompt step carries far more than a server verify.
- A profile of the 4-token prompt step puts 52 % of the GPU time in llama.cpp's stock multi-token expert kernels
  (gate/up 25.7 ms, down 16.7 ms).
- The curve **measured** interpolates linearly between the three points and continues the last segment above 4.05
  tokens, +1.16 T1 per token; up to 8 tokens that stays below the llama-bench bounds. Nothing is measured above 8, so two
  extensions bracket it: **last slope** keeps +1.16 T1 per token, **prompt rate** (`measured+pp` in the script's
  output) adds only 0.197 T1 per token above 8, the pp512 rate.

| n | 2 | 3 | 4 | 5 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|---|
| v(n), T1 | 1.65 | 2.34 | 3.50 | 4.65 | 8.12 | 17.4 / 9.69 | 35.8 / 12.8 | 72.8 / 19.2 |
| Tokens per T1 if every drafted token is accepted | 1.22 | 1.28 | 1.14 | 1.07 | 0.99 | 0.92 / 1.65 | 0.89 / 2.49 | 0.88 / 3.34 |

v(2)–v(4) are interpolated (v(2) between 1 and 2.9 tokens, the least certain), v(5)–v(8) extrapolated, and above 8 the
two extensions are given as last slope / prompt rate. A fully accepted 2-token draft (width 3) gives 1.28 tokens per T1,
the most of any width up to 8; at width 8 even full acceptance is slower than plain decoding.

**Model curves**, from before the measurement ([speculation plumbing](../../docs/research/notes/speculation_plumbing.md)
section 6.1). They show what the drafters would give if multi-token verifies were as cheap as the note assumed:

| Curve | v(2) | v(3) | v(8) | v(16) | v(32) | v(49) | v(65) | Basis |
|---|---|---|---|---|---|---|---|---|
| optimistic | 1.36 | 1.43 | 1.80 | 3.15 | 6.30 | 9.65 | 12.8 | 1.28 T1 + 2 ms per extra token |
| mid | 1.49 | 1.70 | 2.74 | 4.42 | 7.76 | 11.3 | 14.7 | 1.28 T1 + 5.6 ms per extra token |
| Q51 | 1.63 | 1.99 | 3.30 | 4.95 | 7.74 | 9.75 | 12.8 | Bytes read, with the distinct experts Q51 measured for n tokens |
| pessimistic | 1.68 | 2.07 | 3.89 | 6.39 | 10.2 | 12.9 | 14.6 | Bytes read, with random routing |

- T1 there is 26.8 ms (llama-bench). Every n ≥ 2 runs llama.cpp's stock multi-token kernels, hence the base of 1.28 T1
  (the token without the fork's Pascal kernels).
- No verify is cheaper per token than prompt processing: v(n) ≥ 0.197 n T1 (~190 tokens/s pp512 against 37.4 tokens/s
  decoding). This floor sets the optimistic curve from n = 10 on; the other curves above n = 16 extend their formulas.
- At n = 3 and 4 the measured costs are 1.4 and 1.8 times the mid curve's.

**Graph costs.** With Q52 (one CUDA graph and one built graph per verify width) a change of width costs nothing. Without
it ("without Q52"), the step that changes the width costs a rebuild and an uncaptured step (0.15 + 0.18 T1) and the next
step of the same width a capture (0.35 T1), as in the note's section 1.6. The measured points are steady runs at one
width, so these switching costs come on top of them.

- **Flint mostly reasons.** 66 % of the decode tokens are reasoning; 91 % of the edit outputs are. Five of the eight edit
  prompts used all 3,072 tokens before the rewrite began, so only three file rewrites are in the data (2,159 tokens).
- **Code copies from its own reasoning.** A third of a code answer repeats Flint's own earlier output, in runs of ~25
  tokens; three quarters of that is code it drafted while reasoning. Edit reasoning is half copied, in runs of ~30
  tokens, about equally from the input file and from its own earlier reasoning.
- **Fresh text rarely matches, and a match there is rarely right.** Before 1–6 % of fresh tokens the context has a
  6-token match, and its next token is the one Flint generates 14–22 % of the time. Inside a copy, a 6-token match exists
  before 37–98 % of the tokens and continues correctly 95–99 % of the time.
- Against the workload table assumed in the speculation note: chat copies 3.9 % (assumed 3 %) in runs of 10 (assumed
  20); code 21 % (assumed 10 %) in runs of 21 (25); file rewrites 99 % (97 %) in runs of 357 (400). The "edit that keeps
  context" (assumed 75 % in runs of 80) does not occur as such: Flint's edits are reasoning that half-quotes the file,
  then a rewrite. False matches in fresh text are rarer than assumed (1–6 % of steps against 3–8 %) and less often right
  (14–22 % against 35–40 %).

- **Only 2-token drafts pay, and little.** `ngram-copy` with 2-token drafts and no long state gives chat 0.99, code
  1.02, edits 1.08, file rewrites 1.26, 1.03 overall (1.01 without Q52), within 0.02 of the bound for a perfect copy

  much better: even a fully accepted 2-token draft gives only 1.28 tokens per T1.
- **Q53's long state loses**: an 8-token verify costs 8.1 T1 for at most 8 tokens, so Q53 as designed gives 0.97
  overall and 0.97 on rewrites; a long block of 3 tokens (width 4) is break-even (1.01).
- **Every llama.cpp drafter setting loses** on code, edits and overall at the last slope: `ngram-mod` 12/2/8 0.95,

- **Wide blocks depend on the unmeasured widths.** At the prompt-rate extension the 48–64-token defaults give 2.5–2.7× on

  llama.cpp's stock multi-token kernels; the expert products alone take 52 % of a 4-token step.

At 38.6 tokens/s (the rig's plain step), 2-token `ngram-copy` would give ~38 tokens/s on chat, ~39 on code, ~42 on
Flint's edits and ~49 on file rewrites.

## What it means for Q53

These points hold for batched verification. Pipelined speculation (next section) has no draft length or verify width,
and long copies pay in full there.

- **At the measured verify cost, drop the long state: draft 2 tokens per match (verify width 3) and nothing longer.** It
  gives 1.03 overall (chat 0.99, code 1.02, edits 1.08, file rewrites 1.26), within 0.02 of the bound for that width,
  and stays at 1.03 under both extensions above 8 tokens. Q53 as designed gives 0.97. With one draft width, Q52 needs
  only two graph shapes (1 and 3) and is worth 1.01 → 1.03.
- **Keep the 6-token minimum match** (fresh text has a match before only 1–6 % of tokens, and its continuation is right
  14–22 % of the time) **and the 12-token longest match.** 2-token drafts beat 1-token drafts on rewrites (1.26 against

- **Wide blocks are a bet on v(16)–v(64).** If a verify of 16–64 tokens costs close to the prompt-processing rate per
  token, blocks of 31–63 tokens on long copies give 2.1–2.6× on rewrites at no cost elsewhere (overall 1.01–1.03, against
  1.03 without them); if the measured slope continues, they lose 6–30 %. Measure v(16), v(32) and v(64) the same way (server synth
  runs) before building more than the 2-token drafter. Blocks of 4–8 tokens lose under both extensions.
- **If wide blocks pay, add them as a tier above the 2-token drafts, without the 7-token tier**: 2/15/31 or 2/63 avoid
  the 8-token verifies that cost more than they yield. Their costs: more graph shapes for Q52, 32–64 sampler chains in

  width × context, 2 MiB per card for a 32-token step at 32k (Q65).
- **The multi-token kernels decide how much speculation can give Flint on this rig.** At n = 3 and 4 the measured verify

- **Replace the workload table** with the measured copy structure above.
- **With stock drafters, leave speculation off for Flint.** At the measured cost every llama.cpp setting replayed here

## Pipelined speculation (Q87)

Batched verification checks a draft in one multi-token step, which costs 2.2–3.6 plain steps on these cards. Pipelined
speculation has no such step ([breakthrough candidates](../../docs/research/notes/breakthrough_candidates.md),
candidate 1). On a layer split only one card works at a time, so a guess for token t+1 enters card 1 as soon as card 1
has finished token t, while the later cards still work on t; the next guess follows one stage later, up to one per card.
Every guess is an ordinary one-token step on the fork's kernels. The last card samples the real token: a matching guess
is already on its way, a wrong one is cancelled with everything behind it. Sample-and-match keeps the output identical
to plain decoding.

### Model

[pipeline_sim.py](pipeline_sim.py) replays each transcript through an event-by-event model of the cards:
- **Stage times.** Card j runs one stage per token: its layers times a per-layer time, plus 2.5 ms for the output head
  and sampling on the last card. A hop between cards (activations staged through the host, event query, launch) costs
  0.3 ms, and the host needs 1.5 ms from a sample to the next launch on card 1. The per-layer time follows from the
  measured time per plain token, which is that gap plus the stages and the hops.
- **Pipeline.** A token starts on a card one hop after it has left the previous card and the card has finished the token
  before it. Up to `depth` guesses (cards − 1 unless stated) are in flight past the newest verified token; a guess enters
  card 1 one hop after card 1 is free and a slot is open. After a miss, or when there is no guess, the sampled token
  enters 1.5 ms after its sample.
- **Cancellation.** A miss cancels every token behind it: stages already running finish (CUDA work cannot be
  withdrawn), stages not yet started are dropped. With these stage times card 1 has always finished the cancelled guesses
  before the sampled token arrives, so a wrong guess costs card work but no time.
- **Guessers** see the verified tokens plus the guesses in flight:
  - the copy lookup of `ngram-copy` at minimum match lengths 2–12 (it agrees with the replay's `ngram-copy` lookup at
    every position checked);
  - a fixed 4-token key, the lookup `ngram-simple` and `ngram-map-k` use;
  - `ngram-cache`'s 1–4-gram counts, alone and behind the copy lookup;
  - a drafter that is right with probability p at every token (an oracle with a fixed acceptance: the target for a
    trained one-token drafter), alone and behind the copy lookup.
- **Card setups:**

| Setup | Time per plain token | Stage ms per card | Plain tokens/s | Every card busy: one token per slowest stage + hop |
|---|---|---|---|---|

| 9 cards, 6/6/6/6/5/5/5/5/5 layers | 31.3 ms (real chat, Q58) | 3.05 (4 cards) / 2.54 (4 cards) / 5.04 | 32.0 | 187 (5.9×) |
| 9 cards, 6/6/6/6/6/6/6/5/2 layers | 31.3 ms | 3.05 (7 cards) / 2.54 / 3.52 | 32.0 | 262 (8.2×) |

The output head makes the last card the slowest stage. On six cards the VRAM leaves no room to move layers off it (a

- Q53's design questions (draft lengths, tiers, verify widths, Q52's per-width graphs) belong to batched verification.

## A continuation table behind the copy lookup (Q96)

Fresh text is where Q87's guessers miss: the copy lookup guesses only inside copies, and `ngram-cache` only where its
1–4-gram counts pass their thresholds. [Unconventional ideas](../../docs/research/notes/unconventional_ideas.md) (idea 4)
proposes a datastore of Flint's own outputs behind the copy lookup: the most frequent next token after the longest
matching context.

### Method

- **The table.** Next-token counts after every 1- to 8-token context of the generated tokens of Q51's transcripts. Each
  transcript is replayed against the table of the other 37 (leave one out, ~64k tokens), so a guess never comes from the
  text being guessed. Smaller tables (a quarter and half of the transcripts, chosen at random) give the effect of size.
- **Guessers.** The table's most frequent continuation of the longest context it has seen, which always guesses; the
  same with the current request's own counts added ("request counts", the prompt and output so far, contexts up to 8
  tokens); the request counts alone; each behind the copy lookup (match ≥ 4); and a variant that guesses only when its
  token holds at least 30 % of the context's counts.
- **Accuracy.** One token ahead on the transcript's own prefix, split into fresh text and copied text (copies of ≥ 8
  tokens, as above), alongside the pipeline runs of Q87's model.

### Gumbel-coupled guesses

- **Coupling.** The sampler draws each token as the argmax of log p + G over the tokens Flint's sampler chain keeps,
  where G is Gumbel noise keyed by position and token: an exact sample, so the output does not change. A guesser with a
  distribution q guesses the argmax of log q + G with the same noise. With G = −log E and E exponential, token i wins
  both draws when every other token's E exceeds E_i · max(p_j/p_i, q_j/q_i), so the guess matches with probability
  Σ_i 1 / Σ_j max(p_j/p_i, q_j/q_i); an uncoupled top guess matches with p(top guess).
- **Flint's p.** [logit_dump](logit_dump/logit_dump.cpp) (`llama-logit-dump`) ran Flint Q8_0 over the 38 transcripts
  (teacher forcing, two GPUs of the quant machine) and kept the top-20 log-probabilities at every generated position;
  the chain the transcripts were sampled with (temperature 1, top-k 20, top-p 0.95, min-p 0.05) gives p. 99.81 % of the
  transcripts' tokens lie in the kept set.
- **Flint is nearly deterministic at its own settings:** the kept set holds 1.69 tokens on average, the most likely
  token holds 0.90 of the probability on average, and it was the sample 89.7 % of the time.

- **Coupling does not help count-based guessers.** Their counts spread over continuations where Flint is sure, so a
  coupled guess follows the counts' spread where the top guess would have matched Flint's top token: 39.7 → 38.6 % right,
  1.44× → 1.42× on six cards. Sharpened counts only catch up with the top guess (39.9 % at the 8th power).
- **It helps a drafter whose distribution is close to Flint's**: +6 points at σ 0.5 (89.2 → 95.1 %), +4 at σ 1, +2.4 at
  σ 2. On the oracle sweep above that is worth +0.15–0.5× on six cards (p 0.87 → 0.92 at σ 1: ~3.05× → ~3.3×).
- **Without coupling, Flint's own top-token probability caps any drafter**: 0.90 on average, 0.83 on agent turns.
  Coupling lifts that cap to 1, so a trained pipeline drafter (Q20) should output a calibrated distribution and be
  coupled; the n-gram and table guessers should guess their top token.

## A datastore of Flint's own answers (Q161)

A suffix array over 3–14 M generated tokens of other Flint answers, asked after the request's own counts of contexts of
2 tokens or more: chat, code and edits gain ~5 % over `cont` at depths 1–4 on nine cards, all classes 1.44 → 1.52 at
depth 3, and more data barely helps (1.50 → 1.52 from 3 to 13.8 M tokens). Tool calls gain 1.18 → 1.74, but only from
answers that use the same tools. Tables, the held-out check and the cost are in
[pipelined_speculation.md](../../docs/research/notes/pipelined_speculation.md) ("A datastore of Flint's own answers").

- [datastore.cpp](datastore.cpp): the store (a library for ctypes and a `datastore build` command); it counts its work
  per lookup instead of timing it.
- [datastore_corpus.py](datastore_corpus.py): token streams from generated answers in bench/staircase_drafter's format,
  leaving out any answer whose prompt shares a 12-word span with a Q51 prompt.
- [datastore_sim.py](datastore_sim.py): a brute-force self-test of the store, the one-token accuracy of chains with the
  store (per stage), and pipeline_sim.py's nine-card model.

## Gaps

- **File rewrites are 2,159 tokens from three files.** Flint reasoned 1,200–3,000+ tokens before every rewrite, and five
  of the eight edit prompts ran out of their 3,072 tokens while still reasoning. The rewrite numbers are the ones with
  the most leverage and the least data. With room for a full rewrite after the reasoning, rewrites would be 25–35 % of an
  edit output instead of 9 %, and the edit class would move from 1.08 to ~1.10–1.12 at the measured cost with 2-token
  drafts (1.36 to ~1.5–1.6 for the tiered controller at the mid curve; harmonic mix of the reasoning and rewrite rates).
- **No real agent sessions.** The agent class is 10 single turns (6 first turns, 4 after one `read_file` result): 2,953
  tokens, 89 % reasoning, 320 tokens of tool calls (paths, shell commands, search patterns), none of them an edit. Real
  coding-agent sessions emit edit calls whose arguments copy file contents (old and new strings, whole files), carry
  20–100k tokens of tool output and earlier turns, and drop earlier reasoning. A session's speed-up is the harmonic mix
  1 / Σ (share / speed-up) of its parts: 60 % reasoning, 25 % copied tool arguments and 15 % prose give 1.09 at the
  measured cost with 2-token drafts (1.06, 1.26 and 1.0 for the parts) and 1.46 at the mid curve with the tiered
  controller (1.3, 3.5 and 1.0); the single turns here give 1.00 and 1.04. The share of copied tool arguments decides
  it, and no transcript here measures it. Next data: two or three recorded coding-agent sessions replayed with their tool outputs (the replayed agent
  set Q53's rig test already needs), then this replay on them.
- **Verify cost.** v(2) is interpolated and every width above 4 extrapolated from the server measurements; the
  conclusions about blocks wider than 8 tokens rest on which extension holds.
- **The pipeline is a model.** Its stage times come from layer counts and the measured time per token, not from a
  rig run with every card busy; the host's cost per stage launch, the attention-mask copies to every card for every
  token in flight, and clock speed under the power limit are not in it.
- **Long contexts.** All prompts are under 2,100 tokens. A long context offers more true and more false matches; the
  replay does not show how many.
- **Multi-turn chat**, where earlier answers stay in the context, is not covered.
- **Sampling.** The transcripts are at temperature 1.0; copies continue correctly 95–99 % of the time. Greedy or
  low-temperature use (common for tool calls) would copy at least as faithfully.
- **Host costs not in the model:** the logits copy per verified row without backend sampling (requests with tools; ~0.11
  T1 per row, the note puts it at ~4 points of an agent session's gain), the drafter's own lookup, and the mask copies
  at depth (Q65).

## Running it

```bash
# the transcripts: bench/expert_overlap's generate.py writes gen.jsonl
python -I replay.py gen.jsonl --out q64.json > q64.md             # ~1 min on one core, standard library only
# with the rig's verify step times (Q19 stage 1, ms) and llama-bench pp-n as upper bounds above them
python -I replay.py gen.jsonl --vn 1=25.9,2.9=57.7,4.05=92.1 --vn-cap 5=163.6,6=170.0,7=207.6,8=212.1 > q64_measured.md
LLAMA_DIR=<llama.cpp fork checkout> bash fork_check.sh gen.jsonl  # needs g++; checks the ports against the fork's C++
python -I pipeline_sim.py gen.jsonl --out q87.json --jobs 8 --accuracy > q87.md   # pipelined speculation, ~1 min on 8 cores
# Flint's top-20 log-probabilities along the transcripts: build logit_dump/ inside a llama.cpp tree (as its CMakeLists
# says), then LOGIT_IN=seqs.txt LOGIT_OUT=top20.bin llama-logit-dump -m flint-Q8_0.gguf -ngl 99 -c 6144 -fa on
python -I pipeline_sim.py gen.jsonl --jobs 8 --topk top20.bin --only 'Gumbel|expected' > q96_coupled.md
python -I pipeline_sim.py gen.jsonl --topk top20.bin --coupling-study > q96_coupling_study.md
# Q161: the datastore (standard library Python; g++ for the store)
g++ -O2 -std=c++17 -shared -fPIC -o libdatastore.so datastore.cpp && g++ -O2 -std=c++17 -DDS_MAIN -o datastore datastore.cpp
python -I datastore_corpus.py corpus <prompts.jsonl> <q51 prompts.jsonl> <generated answers .jsonl ...>
./datastore build corpus/clean.i32 14000000 clean-14M.ds          # the first 14 M tokens; 3000000 for a 3 M store
python -I datastore_sim.py gen.jsonl --lib ./libdatastore.so --store clean-14M=clean-14M.ds --selftest corpus/clean.i32 \
    --policies 'L >= 2, share >= 0.3' --kinds ds,req2ds --accuracy --sim --depths 1,2,3,4 --jobs 8 --out q161.json
```

`replay.py` prints the copy-structure tables and, per class, per segment and for the file rewrites, every drafter
setting with its draft share, acceptance, tokens per step, widths and speed-up at each curve (`measured` and
`measured+pp` when `--vn` is given); `--out` writes the same as
JSON, including the full width histograms. `--only REGEX` limits the drafter settings, `--dump-steps FILE` writes every
step. `pipeline_sim.py` prints the card setups and, for every setup, guesser, depth and sensitivity run, the speed-up per
workload with the shares of right and wrong guesses; `--out` adds tokens/s; the setups, hop, gap and head time are
constants at the top of the script. `--accuracy` adds the one-token accuracy of the guessers on fresh and copied text
and the table-size curve; `--only REGEX` limits the runs.
