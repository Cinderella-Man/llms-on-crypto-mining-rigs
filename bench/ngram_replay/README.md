# Replaying n-gram drafters on Flint's own output (Q64)

Which draft-model-free speculative decoding pays for Flint on the P106 rig, and for which kind of work? Flint routes
every verified token to 6 of 256 experts with little locality ([Q51](../expert_overlap/README.md)), so a verify step of
n tokens costs a lot, and only drafts that are almost always accepted pay. The cheapest drafters copy from the context.
This replays every n-gram drafter in llama.cpp, and the copy-gated `ngram-copy` drafter designed for Q53
([speculation plumbing](../../docs/research/notes/speculation_plumbing.md) section 5), on transcripts Flint generated
itself, with exact acceptance, and turns the step counts into speed-ups with a verify-cost table (registry row Q64 in
[quants/experiments.md](../../quants/experiments.md)).

## Method

- **Data.** Q51's transcripts ([expert_overlap](../expert_overlap/README.md)): 38 prompts (10 chat, 10 code writing,
  8 whole-file edits of this repository's scripts, 10 agent turns with four coding tools), generated by Unsloth's Flint
  Q8_0 at its default sampling (temperature 1.0, top-k 20, top-p 0.95, min-p 0.05), up to 3,072 tokens each, with exact
  prompt and output token ids. 65,520 tokens come from decode steps (the first token of each answer comes from the
  prompt pass). Flint's own tokens split each output into reasoning (`<think>` … `</think>`), tool calls
  (`<tool_call>` … `</tool_call>`) and answer text.
- **Replay.** [replay.py](replay.py) steps through each output as llama-server does: at every step the drafter gets
  the tokens in the KV cache and the last sampled token, and the draft is cut to the room the server allows (context
  and `n_predict`). The step keeps the longest prefix of the draft that equals what Flint generated next and yields
  that many tokens plus one. A drafter hears the accepted count only after a non-empty draft, as in the server.
- **Why the acceptance is exact.** The server verifies n-gram drafts by sample-and-match: it samples each position from
  the target and keeps a draft token while the sample equals it. The transcripts are samples from the target at the same
  settings, so the count of kept tokens on this output is the count the server would see on the same output.
- **Drafters.** Line-by-line Python ports of the llama.cpp fork's code (branch `pascal-p106`, upstream `d77256999`):
  `ngram-simple`, `ngram-map-k` and `ngram-map-k4v` (`common/ngram-map.cpp`, hash collisions included), `ngram-mod`
  (`common/ngram-mod.cpp` and its driver in `common/speculative.cpp`), `ngram-cache` without cache files
  (`common/ngram-cache.cpp`, at most 8 tokens). [fork_check.sh](fork_check.sh) compiles the fork's three source files
  unchanged with stub headers, drives them with [fork_check.cpp](fork_check.cpp), and compares every step: all 15
  llama.cpp settings below draft the same lengths and accept the same counts at every one of their 45,000–62,000 steps.
  `ngram-mod` shares its table across requests in the server, and `ngram-cache` keeps its counts; here every request
  starts empty, as on a freshly started server.
- **`ngram-copy`** follows Q53's design: the longest match of the context's suffix, 6 to 12 tokens, newest on ties,
  allowed to overlap the suffix (it then continues periodically); 2 drafted tokens per match; 7 after two fully
  accepted steps in a row, while the match has 7 tokens of continuation or is periodic; the long state is held through
  2 missed steps. The sweep varies one parameter at a time. **Tiers** `2/7/15/31` is a variant: the controller climbs
  one tier after every two fully accepted steps and falls back to 2 tokens as the long state does.
- **Copy structure**, independent of any drafter: a greedy longest-previous-match parse of each output against its
  prompt and its own earlier output (sources may overlap the copy). Tokens inside matches of at least 8 tokens count as
  copied; back-to-back copies form a copy run.
- **Bounds.** "Oracle copy" sees the output and drafts exactly the rest of the current copy (≥ 8 tokens), capped at k,
  so it is always accepted and never drafts fresh text. "After 6" waits until 6 tokens of the copy have been generated,
  as any drafter that needs a 6-token key must.

### Cost model

Speed-up = (decode steps without drafting) / Σ over steps of v(width) + graph costs, where v(n) is the time of a decode
step that verifies n tokens, in T1 (one plain token with the fork's Pascal kernels: 26.8 ms for the S4-L0 mix on six
cards). Until the rig's measurement (Q19 stage 1) arrives, the curves are those of
[speculation plumbing](../../docs/research/notes/speculation_plumbing.md) section 6.1, which are estimates, not
measurements:

| Curve | v(2) | v(3) | v(8) | v(16) | v(32) | v(49) | v(65) | Basis |
|---|---|---|---|---|---|---|---|---|
| optimistic | 1.36 | 1.43 | 1.80 | 3.15 | 6.30 | 9.65 | 12.8 | 1.28 T1 + 2 ms per extra token |
| mid | 1.49 | 1.70 | 2.74 | 4.42 | 7.76 | 11.3 | 14.7 | 1.28 T1 + 5.6 ms per extra token |
| Q51 | 1.63 | 1.99 | 3.30 | 4.95 | 7.74 | 9.75 | 12.8 | Bytes read, with the distinct experts Q51 measured for n tokens |
| pessimistic | 1.68 | 2.07 | 3.89 | 6.39 | 10.2 | 12.9 | 14.6 | Bytes read, with random routing |

- Every n ≥ 2 runs llama.cpp's stock multi-token kernels, hence the base of 1.28 T1 (the kernels-off token).
- No verify is cheaper per token than prompt processing: v(n) ≥ 0.197 n T1 (~190 tokens/s pp512 against 37.4 tokens/s
  decoding). This floor sets the optimistic curve from n = 10 on; the other curves above n = 16 extend their formulas.
- **Graph costs.** With Q52 (one CUDA graph and one built graph per verify width) a change of width costs nothing. Without
  it ("today"), the step that changes the width costs a rebuild and an uncaptured step (0.15 + 0.18 T1) and the next
  step of the same width a capture (0.35 T1), as in the note's section 1.6.
- `--vn 1=26.8,2=...,8=...` adds a measured table as the curve "measured" (any unit, divided by v(1); beyond its last
  point it extends the last segment's slope, never below the prompt-processing floor).

- **Flint mostly reasons.** 66 % of the decode tokens are reasoning; 91 % of the edit outputs are. Five of the eight edit
  prompts used all 3,072 tokens before the rewrite began, so only three file rewrites are in the data (2,159 tokens).
- **Code copies from its own reasoning.** A third of a code answer repeats Flint's own earlier output, in runs of ~25
  tokens; three quarters of that is code it drafted while reasoning. Edit reasoning is half copied, in runs of ~30
  tokens, about equally from the input file and from its own earlier reasoning.
- **Fresh text rarely matches, and a match there is rarely right.** Before 1–6 % of fresh tokens the context has a
  6-token match, and its next token is the one Flint generates 14–22 % of the time. Inside a copy, a 6-token match exists
  before 37–98 % of the tokens and continues correctly 95–99 % of the time.
- Against the workload table assumed in the speculation note: chat copies 3.9 % (assumed 3 %) in runs of 10 (assumed
  20); code 21 % (assumed 10 %) in runs of 21 (25); file rewrites 99 % (97 %) in runs of 357 (400). The "edit that keeps
  context" (assumed 75 % in runs of 80) does not occur as such: Flint's edits are reasoning that half-quotes the file,
  then a rewrite. False matches in fresh text are rarer than assumed (1–6 % of steps against 3–8 %) and less often right
  (14–22 % against 35–40 %).

- **Chat gains nothing from any drafter**, and drafters with short keys lose: `ngram-cache` 0.92, `ngram-simple` 3/4
  and `ngram-map-k` 4/8 0.98 (0.94–0.96 at the pessimistic curve).
- **Long verbatim blocks pay on file rewrites.** The defaults with 48–64-token drafts reach 3.4–3.6×. At the mid curve a
  49-token verify costs 11.3 T1, 0.23 T1 per token, close to the prompt-processing rate, against 2.74 T1 for 8 tokens,
  0.34 T1 per token. Q53's 7-token cap gives 2.71×.
- **Short drafts pay on reasoning and code**, where copies are ~15–30 tokens long: Q53 gives 1.08 on code and 1.33 on
  edits, where the 48–64-token defaults give 1.01 and 1.20.
- **The tiered controller gets both:** chat 1.00, code 1.08, edits 1.36, rewrites 3.52, all 1.14.
- **Most of what copying can give is taken.** Q53 gets 83 % of the gain of the ≤ 7 bound that also waits for a 6-token
  key (0.133 of 0.161 overall), the tiered controller 75 % of the ≤ 31 one's (0.141 of 0.187). The difference is the
  2-token entry steps, blocks that run past the end of a copy, false matches, and matches on another occurrence than the
  copy's source.
- **Without Q52**, Q53 and the tiered controller lose ~3 % overall (1.13 → 1.10, 1.14 → 1.11), `ngram-mod`'s rare long
  drafts almost nothing, and ungated drafters most (`ngram-cache` 1.02 → 0.92, `ngram-simple` 3/4 1.11 → 1.03).

Width of the verify steps over all classes: Q53 verifies 1 token at 93.5 % of steps, 3 at 3.4 % and 8 at 3.1 %; the
tiered controller 1 / 3 / 8 / 16 / 32 tokens at 94.6 / 3.4 / 1.3 / 0.4 / 0.3 %; `ngram-mod`'s default 1 or 65 tokens
(99.6 / 0.4 %); `ngram-simple`'s default 1 or 49 (98.9 / 1.0 %).

## What it means for Q53

- **Add tiers above 7: 15 and 31 drafted tokens (verify widths 16 and 32), one tier up after every two fully accepted
  steps, back to 2 tokens as the long state falls back.** File rewrites gain 30 % (2.71 → 3.52 at the mid curve, 2.28 →
  3.43 at Q51's), everything else stays within ±1 %. The note's conclusion that blocks above 7 need expert locality does
  not hold for verbatim copies: when nearly every drafted token is accepted, a wide verify approaches the
  prompt-processing rate per token.
- **Costs to check before taking them:** Q52 then keeps five widths (1, 3, 8, 16, 32), within PR #31004's 8 graphs per
  card; backend sampling builds 1 + 31 = 32 sampler chains into every graph, plain steps included (cost unmeasured);
  and the attention masks crossing every x1 link grow with width × context, 2 MiB per card for a 32-token step at 32k
  (Q65). Until Q65 measures that, cap the top tier by context depth.
- **Keep the rest of the design:** the 6-token minimum match (fresh text has a match before only 1–6 % of tokens, and
  its continuation is right 14–22 % of the time), the 12-token longest match, 2-token short drafts, entry after two full
  steps and a hold of 2.
- **Replace the workload table** with the measured one above, and the expected gains: chat 1.00, new code 1.05–1.11,
  Flint's whole-file edits as it does them (91 % reasoning) 1.25–1.45, file rewrites 2.7–4.3, single agent turns
  1.02–1.06 (tiered controller, with Q52).
- **Without any fork change**, `--spec-default` (`ngram-mod` 24/48/64) is the safe choice for Flint today: never below
  1.00 on any class at any curve, 1.07–1.08 overall and 3.4–3.7× on file rewrites. It puts 65 sampler chains into every
  graph with `-bs` and 65-token verifies against the masks, both unmeasured on the rig.
- **Q19 stage 1** should measure v(16) and v(32), not only 1–8: the tier decision rests on them.

## Gaps

- **File rewrites are 2,159 tokens from three files.** Flint reasoned 1,200–3,000+ tokens before every rewrite, and five
  of the eight edit prompts ran out of their 3,072 tokens while still reasoning. The rewrite numbers are the ones with
  the most leverage and the least data. With room for a full rewrite after the reasoning, rewrites would be 25–35 % of an
  edit output instead of 9 %, and the edit class would move from 1.36 to ~1.5–1.6 at the mid curve (harmonic mix of the
  measured reasoning and rewrite rates).
- **No real agent sessions.** The agent class is 10 single turns (6 first turns, 4 after one `read_file` result): 2,953
  tokens, 89 % reasoning, 320 tokens of tool calls (paths, shell commands, search patterns), none of them an edit. Real
  coding-agent sessions emit edit calls whose arguments copy file contents (old and new strings, whole files), carry
  20–100k tokens of tool output and earlier turns, and drop earlier reasoning. A session's speed-up is the harmonic mix
  1 / Σ (share / speed-up) of its parts: 60 % reasoning at 1.3, 25 % copied tool arguments at 3.5 and 15 % prose at 1.0
  give 1.46; the measured single turns give 1.04. The share of copied tool arguments decides it, and no transcript here
  measures it. Next data: two or three recorded coding-agent sessions replayed with their tool outputs (the replayed agent
  set Q53's rig test already needs), then this replay on them.
- **Long contexts.** All prompts are under 2,100 tokens. A long context offers more true and more false matches; the
  replay does not show how many.
- **Multi-turn chat**, where earlier answers stay in the context, is not covered.
- **Sampling.** The transcripts are at temperature 1.0; copies continue correctly 95–99 % of the time. Greedy or
  low-temperature use (common for tool calls) would copy at least as faithfully.
- **Host costs not in the model:** the logits copy per verified row without backend sampling (requests with tools; ~0.11
  T1 per row, the note puts it at ~4 points of an agent session's gain), the drafter's own lookup, and the mask copies
  at depth (Q65).

## Running it

```bash
# the transcripts: bench/expert_overlap's generate.py writes gen.jsonl
python -I replay.py gen.jsonl --out q64.json > q64.md             # ~1 min on one core, standard library only
python -I replay.py gen.jsonl --vn 1=26.8,2=...,8=... > q64_measured.md   # with the rig's v(n), in ms or T1
LLAMA_DIR=<llama.cpp fork checkout> bash fork_check.sh gen.jsonl  # needs g++; checks the ports against the fork's C++
```

`replay.py` prints the copy-structure tables and, per class, per segment and for the file rewrites, every drafter
setting with its draft share, acceptance, tokens per step, widths and speed-up at each curve; `--out` writes the same as
JSON, including the full width histograms. `--only REGEX` limits the drafter settings, `--dump-steps FILE` writes every
step.
