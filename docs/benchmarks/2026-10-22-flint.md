# Flint: the fastest model on the rig so far

*Measured 2026-10-22.*

[Flint](https://huggingface.co/RecursiveSI/flint) is a Mixture-of-Experts model released on 2026-10-20 by Recursive.
It stores 39.8 billion parameters but uses about 2.5 billion per token, and its makers position it for agentic coding.
llama.cpp gained support for it on 2026-10-21 ([PR #30928](https://github.com/ggml-org/llama.cpp/pull/30928)), so it
needs a build from that date or later; the build used here was made with
[scripts/build_llamacpp_docker.sh](../../scripts/build_llamacpp_docker.sh).

## The model

| | |
|---|---|
| Layers | 49: 14 with full attention and 35 with sliding-window attention over the last 513 tokens; the first two are dense, the rest Mixture-of-Experts |
| Experts | 256 per layer, 6 used per token, plus one shared expert |
| Attention | 32 query heads and 4 key-value heads of 128 dimensions, with learned attention sinks |
| Native context | 262,144 tokens |
| KV cache | ~28 KiB per token (only the 14 full-attention layers keep the whole context), so 262,144 tokens take ~7 GiB in f16 |
| File tested | [RecursiveSI/flint-int4-gguf](https://huggingface.co/RecursiveSI/flint-int4-gguf) `flint-int4-q4_1.gguf`, 26.0 GB, Q4_1 quantization from the model's makers |

Q4_1 is a simple 4-bit format (blocks of 32 weights with a scale and an offset), the family that makes the best use of
these cards' memory bandwidth ([single-card calibration](2026-10-22-single-card-calibration.md)). The file keeps the
token-embedding table in 32-bit floats; llama.cpp leaves that table in host memory, where it takes 1.17 GB of the
page cache.

## Setup

| Item | Value |
|---|---|
| Inference engine | llama.cpp commit `d77256999` (2026-10-22), built for compute capability 6.1, with and without CUDA graphs enabled for Pascal ([PR #27721](https://github.com/ggml-org/llama.cpp/pull/27721)) |
| Synthetic benchmarks | [scripts/bench.sh](../../scripts/bench.sh): `llama-bench -ngl 99 -fa on -p 512 -n 128 -r 3`; context depth with `-p 0 -n 64 -d 0,8192,32768 -r 1` |
| Real requests | [scripts/server_bench.sh](../../scripts/server_bench.sh): llama-server with `-c 262144 -b 512 -ub 128`, four chat prompts at temperature 0, 256 generated tokens each |

## Results

### Generation speed

| Build | Cards | Prompt processing, pp512 (tokens/s) | Generation, tg128 (tokens/s) |
|---|---|---|---|
| CUDA graphs enabled | 5 | 170.6 ± 22.6 | **27.92 ± 0.04** |
| CUDA graphs enabled | 9 | 161.1 ± 27.6 | 28.09 ± 0.23 |
| Upstream (CUDA graphs disabled on Pascal) | 5 | 170.0 ± 24.0 | 24.56 ± 0.04 |

Flint generates 1.4 times faster than Qwen3.6-35B-A3B on the same build
([Qwen baselines](2026-10-22-qwen-baselines.md): 19.6 tokens/s with CUDA graphs). CUDA graphs add 14 % here, more than
for Qwen3.6, and the number of cards makes no difference. The 26 GB file needs at least five cards. Prompt processing
is slower than Qwen3.6's and varies from run to run.

### Long context

Generation on five cards with tokens already in the context (one repetition each, so approximate):

| Context already in the cache | 0 | 8,192 | 32,768 |
|---|---|---|---|
| Generation (tokens/s) | 20.4 | 25.7 | 19.5 |

At 32,768 tokens of context Flint still generates 19.5 tokens/s, against 14.0 for Qwen3.6 at the same depth. (The
low value at depth 0 is a single 64-token run and is in line with the same effect seen for Qwen3.6.)

### Real chat requests at the full 262,144-token context

| Prompt | Generated tokens | Generation (tokens/s) |
|---|---|---|
| Code | 256 | 21.61 |
| Explanation | 256 | 21.71 |
| Arithmetic word problem | 239 | 22.89 |
| Rewrite a paragraph | 256 | 23.47 |
| **All four** | **1,007** | **22.47** |

With backend sampling (`-bs`) the same requests run at 24.26 tokens/s ([speed-ups](2026-10-22-speedups.md)).

With the whole 262,144-token context allocated across nine cards, the server uses 33.9 GB of the 54 GB of GPU memory
(2.1–3.0 GB of weights and 0.5–1.5 GB of KV cache per card) and 1.44 GB of host memory: 1.17 GB for the mapped
embedding table and 267 MiB of pinned buffers with `-ub 128`. It loads in 3 min 22 s. The model's bundled chat
template works with this build.

### Two conversations at once

One copy across all nine cards with two parallel slots (`-np 2 -c 524288 -b 512 -ub 128 -bs`, so 262,144 tokens of
context for each conversation), two requests sent together, measured with
[scripts/parallel_bench.sh](../../scripts/parallel_bench.sh):

| Prompt | Conversation 1 (tokens/s) | Conversation 2 (tokens/s) | Combined |
|---|---|---|---|
| Code | 21.19 | 21.72 | 35.4 tokens/s |
| Explanation | 23.64 | 23.63 | 42.4 tokens/s |

Each conversation keeps almost its single-request speed, so the combined output nearly doubles. That is very
different from Qwen3.6-35B-A3B, whose two slots slow to ~13 tokens/s each
([Qwen baselines](2026-10-22-qwen-baselines.md)). The setup uses 3.9–5.5 GB per card and leaves 1.3 GB of host RAM free.

### Quantization: speed against quality

Two 4-bit files of about the same size: the makers' Q4_1 and Unsloth's dynamic
[UD-Q4_K_XL](https://huggingface.co/unsloth/flint-GGUF) (25.1 GB), which mixes K-quant formats and keeps sensitive
tensors at higher precision using an importance matrix. Speed was measured on the rig with the CUDA-graphs build.
Quality was measured on a separate PC with [scripts/quality_kld.sh](../../scripts/quality_kld.sh): llama.cpp's
perplexity on 80 chunks of 512 tokens of wikitext-2, and the KL divergence of each file's next-token distribution from
that of Unsloth's [Q8_0](https://huggingface.co/unsloth/flint-GGUF) (42.3 GB) as the reference. Quality depends only on
the weights, not on the GPU; the method is explained in [Comparing and making quantizations](../../quants/guide.md).

Besides the two published 4-bit files, three quants were made for this comparison with
[scripts/quantize_docker.sh](../../scripts/quantize_docker.sh): requantized from the Q8_0 file with
[Unsloth's importance matrix](https://huggingface.co/unsloth/flint-GGUF) (`imatrix_unsloth.gguf_file`), the output head
kept at Q8_0, everything else in one simple format.

| | Q4_1, makers (26.0 GB) | Q5_0 + imatrix (27.6 GB) | UD-Q4_K_XL, Unsloth (25.1 GB) | Q4_1 + imatrix (25.0 GB) | Q4_0 + imatrix (22.6 GB) |
|---|---|---|---|---|---|
| Generation, tg128, 5 / 9 cards (tokens/s) | **27.9 / 28.1** | 22.3 / 22.8 | 17.4 / 19.0 | — | — |
| Prompt processing, pp512, 5 / 9 cards (tokens/s) | 171 / 161 | **198 / 185** | **199 / 186** | — | — |
| Generation at 8,192 / 32,768 tokens of context (tokens/s) | **25.7 / 19.5** | 19.7 / 17.0 | 17.1 / 14.8 | — | — |
| Real chat requests at 262,144 context, `-bs` (tokens/s) | **24.3** | 18.9 | 15.8 | — | — |
| Perplexity relative to Q8_0 | +3.7 % | +4.6 % | +3.3 % | +5.9 % | +45 % |
| Mean / median KL divergence from Q8_0 | 0.316 / 0.109 | 0.177 / 0.045 | **0.124 / 0.027** | 0.280 / 0.077 | 0.566 / 0.246 |
| 99th-percentile KL divergence | 3.90 | 2.65 | **1.83** | 3.62 | 4.82 |
| Same top token as Q8_0 | 78.6 % | 85.0 % | **87.6 %** | 80.9 % | 71.4 % |

**Q4_1 generates fastest; UD-Q4_K_XL stays closest to the reference; the imatrix Q5_0 sits in between.** The speed
order follows the format: the 5-SM cards unpack the simple Q4_1 and Q5_0 blocks quickly and K-quant blocks slowly
([calibration](2026-10-22-single-card-calibration.md)). Against Q8_0, the makers' Q4_1 picks a different most-likely
token 21 % of the time, UD-Q4_K_XL 12 % and the imatrix Q5_0 15 %. The imatrix Q5_0 is 20 % faster than UD-Q4_K_XL and
recovers most of its fidelity. **Plain Q4_0 is unusable for Flint** (perplexity +45 %). The cause is a handful of
tensors whose inputs have a few dominant channels (the down-projections of layers 46–48, the shared expert's in layer 12,
layer 48's attention output); with those seven tensors at Q8_0, Q4_0 is fine
([quant research](../../quants/research.md#rounding)).

Two caveats. KL divergence measures distance from Q8_0, not task quality: Recursive tuned its own Q4_1 and NVFP4 files
by distillation, so they differ from the original weights by design, and a community test reported the Q4_1 file level
with the full-precision model on tool-calling tasks despite a large KL divergence
([research notes](../research/notes/flint_speedups.md)). And the imatrix quants were made from Q8_0 rather than the
full-precision weights. Task-based checks are the next step for choosing between these files.

The 42.3 GB Q8_0 reference itself needs at least eight cards. On all nine, with the CUDA-graphs build, it generates
20.5 tokens/s (tg128) and processes prompts at 185 tokens/s (pp512): slower than Q4_1 because it reads more bytes, but
faster than UD-Q4_K_XL because its format is cheap to unpack.

### The MoE down-projection rescale

llama.cpp's Flint support divides the input of each expert's down-projection by a power of two and multiplies the
result back ([PR #30928](https://github.com/ggml-org/llama.cpp/pull/30928), using #30861). On CUDA, activations are
packed into 8-bit blocks whose sums are stored in 16-bit floats, and for Q4_0, Q4_1, Q5_0 and Q5_1 weights those sums
can overflow without the rescale. The workaround adds ~11 operations per MoE layer and cannot be switched off by a
flag. A build with a switch for it (the environment variable `LLAMA_NO_MOE_DOWN_RESCALE=1`,
[patches/moe-down-rescale-env.diff](../../patches/moe-down-rescale-env.diff)) gave:

| File | Cards | tg128 with rescale (tokens/s) | tg128 without (tokens/s) | Perplexity on the GPUs without the rescale |
|---|---|---|---|---|
| Q4_1 (makers) | 5 | 28.05 | 30.31 (+8 %) | **NaN on every chunk** (19.29 with the rescale) |
| Q5_0 + imatrix | 5 | 21.33 | 23.76 (+11 %) | not tested |
| Q8_0 (Unsloth) | 9 | 20.49 | 21.57 (+5 %) | not yet tested; expected exact, since Q8_0 doesn't use the 16-bit sums |

**The rescale is required for Flint's 4- and 5-bit files**: without it Q4_1 produces NaN, so Flint's activations
are larger than the workaround's safety margin. It is unnecessary for formats without the 16-bit sums (Q8_0, IQ4_NL
and others), which opens a route to the speed gain: a quant whose expert down-projections are Q8_0 or IQ4_NL while the
rest stays Q4_1, run without the rescale. Two such files were made (imatrix Q4_1 elsewhere) and scored against
Q8_0; their speed on the rig is still to be measured:

| Quant (imatrix) | Size | Same top token | Mean KL divergence | Perplexity vs Q8_0 |
|---|---|---|---|---|
| Q4_1 | 25.0 GB | 80.9 % | 0.280 | +5.9 % |
| Q4_1, expert down-projections IQ4_NL | 24.3 GB | 80.5 % | 0.281 | +5.9 % |
| Q4_1, expert down-projections Q8_0 | 30.6 GB | 81.5 % | 0.257 | +6.0 % |

Widening the down-projections helps quality only a little. Unsloth's UD-Q4_K_XL (87.6 %) owes its lead mostly to
attention and the shared expert at Q8_0 in most layers and to per-layer bit choices for the experts (Q5_K in 29 of 47
layers for the down-projections, IQ4_XS or Q5_K for gate and up). Mirroring that allocation with formats these cards
decode quickly was the next experiment: the resulting
[UD-mirror v1](../../quants/recipes/flint-udmirror-v1.txt) (27.0 GB; Q5_K→Q5_0, IQ4_XS/Q4_K→Q4_1, Q8_0 kept) scores
87.4 % top-token agreement and KL divergence 0.129, the same as UD-Q4_K_XL within measurement noise. Its speed on the
rig is still to be measured ([quants subproject](../../quants/README.md)).

### Fewer experts per token

llama.cpp can override how many of the 256 experts each token uses
(`--override-kv flint.expert_used_count=int:N`; the model was trained with 6). On the Q4_1 file:

| Experts per token | 6 (trained) | 5 | 4 |
|---|---|---|---|
| Real chat requests at 262,144 context, `-bs` (tokens/s) | 24.3 | 25.1 (+4 %) | 26.4 (+9 %) |
| Perplexity relative to Q8_0 | +3.7 % | +12.8 % | +23 % |
| Mean KL divergence from Q8_0 | 0.316 | 0.379 | 0.555 |
| Same top token as Q8_0 | 78.6 % | 76.7 % | 71.9 % |

The speed gain is small because attention, the shared expert, the output head and per-operation overhead don't change,
and the quality loss is large. Not worth it.

## Interpretation

- **Flint is the best fit for the rig found so far.** It reads less per token than Qwen3.6 (2.5 B parameters at
  ~5 bits), keeps most of its attention local (sliding window), and its KV cache stays small. The result is ~28
  tokens/s raw, ~22.5 tokens/s on real requests, and the full 262,144-token context with room to spare.
- **CUDA graphs matter more for Flint** (+14 %) than for Qwen3.6 (+7 %), consistent with per-operation overhead being a
  large share of its token time.
- **One copy serves two conversations almost for free.** Flint needs five cards, so two copies don't fit, but one copy
  with two parallel slots gives each conversation 21–24 tokens/s and the full 262,144-token context, 35–42 tokens/s in
  total.
