# Making the models faster: quantization, CUDA graphs, multi-token prediction, backend sampling

*Measured 2026-10-22.*

The baselines ([Qwen](2026-10-22-qwen-baselines.md), [Flint](2026-10-22-flint.md)) left four levers that need no new
hardware. This page measures each one and their combination on real chat requests:

| Lever | What it does | How to enable it |
|---|---|---|
| A simpler quantization format | Q4_0 and Q4_1 unpack faster than K-quants on these 5-SM cards ([calibration](2026-10-22-single-card-calibration.md)) | Download a Q4_0/Q4_1 GGUF |
| CUDA graphs | Record each card's sequence of GPU operations once and replay it with one launch, cutting per-operation overhead | A llama.cpp build with [PR #27721](https://github.com/ggml-org/llama.cpp/pull/27721) ([build script](../../scripts/build_llamacpp_docker.sh), `--cuda-graphs-pascal`) |
| Multi-token prediction (MTP) | A small extra layer shipped inside Qwen 3.6/3.8 GGUF files drafts the next tokens; the full model verifies them in one pass | `--spec-type draft-mtp`, optionally `--spec-draft-n-max N` |
| Backend sampling | Picks the next token on the GPU instead of copying ~250,000 scores to the 2-core CPU and sorting them there | `-bs` |

## Setup

llama.cpp commit `d77256999` (2026-10-22) with CUDA graphs enabled for Pascal, `llama-server` through
[scripts/server_bench.sh](../../scripts/server_bench.sh) (four chat prompts at temperature 0; 128 generated tokens per
prompt for the dense model, 256 for Qwen3.6). The dense model ran on four cards from the rig's SSD, Qwen3.6 on nine
cards with a 32,768-token context.

## Dense Qwen3.8-27B: from 3.9 to 7.5 tokens/s

| Configuration | Generation (tokens/s) | Drafted tokens accepted |
|---|---|---|
| UD-Q4_K_M, older build (`85d5703a3`), `llama-bench` | 3.94 | — |
| **Q4_0**, CUDA-graphs build, `llama-bench` | 4.33 | — |
| Q4_0, CUDA-graphs build, server, plain | 4.42 | — |
| + backend sampling (`-bs`) | 4.55 | — |
| + MTP, 1 drafted token per step | 7.43 | 235 / 270 (87 %) |
| **+ MTP, 2 drafted tokens per step** | **7.50** | 302 / 408 (74 %) |
| + MTP, 3 drafted tokens per step (llama.cpp's default) | 7.17 | 335 / 512 (65 %) |
| + MTP, 2 drafted tokens, + backend sampling | 7.33 | 302 / 408 (74 %) |
| + MTP, 2 drafted tokens, only drafts with probability ≥ 0.75 (`--spec-draft-p-min 0.75`) | 6.93 | 263 / 283 (93 %) |
| + MTP, 3 drafted tokens, probability ≥ 0.75 | 7.04 | 282 / 317 (89 %) |

The four levers together almost double the dense model's speed. MTP does most of it, but only with fewer drafted tokens
than llama.cpp's default: on these cards, checking several tokens at once costs noticeably more than checking one.
That cost was measured directly with `llama-bench -p 1,2,3,4,8 -n 0`, which times the model processing 1, 2, 3, 4 or
8 tokens in a single step:

| Tokens checked in one step | 1 (plain generation) | 2 | 3 | 4 | 8 |
|---|---|---|---|---|---|
| Qwen3.8-27B Q4_0: time per step | 231 ms | 307 ms (1.33×) | 394 ms (1.71×) | 402 ms (1.74×) | 621 ms (2.69×) |
| Qwen3.6-35B-A3B Q4_0: time per step | 51 ms | 76 ms (1.49×) | 93 ms (1.82×) | 110 ms (2.15×) | 195 ms (3.82×) |

(Single-token times come from `tg128`; the 2–8-token times from `pp2`…`pp8`.) A step that checks a draft of one token
costs 1.33 times a plain step and yields on average 1.87 tokens at 87 % acceptance, a predicted gain of ~1.4×. The
measured gain is larger (1.68×), so these step times somewhat overstate the cost of a real verification step (even
`pp1` is slower than plain generation, 334 against 231 ms); the trend is what matters. With three drafted tokens, each
step costs ~1.7 times a plain one while acceptance falls to 65 %, so the gain shrinks. On these cards a dense model's best setting is one or two drafted tokens.

A probability threshold for drafts raises acceptance to ~90 % but drafts fewer tokens, and ends up slower than plain
two-token drafting here.

Backend sampling barely matters for the dense model: at ~230 ms per token, the few milliseconds the CPU spends on
sampling are noise.

## Qwen3.6-35B-A3B: from 15.5 to 27.7 tokens/s

| Configuration | Generation (tokens/s) | Drafted tokens accepted |
|---|---|---|
| Older build (`85d5703a3`), plain | 15.51 | — |
| Older build, MTP (separate head file, 3 drafted tokens) | 22.34 | 710 / 920 (77 %) |
| CUDA-graphs build, MTP (layer embedded in the model file, 3 drafted tokens) | 23.44 | 709 / 927 (76 %) |
| **CUDA-graphs build, MTP, backend sampling** | **27.66** | 709 / 927 (76 %) |
| CUDA-graphs build, MTP with 2 drafted tokens, backend sampling | 27.71 | 637 / 759 (84 %) |

For the MoE model, backend sampling is worth 18 % on top of MTP. Its tokens take ~36 ms each, so the CPU sorting
~248,000 candidate scores for every token was a real share of the time. Each step here verifies up to three drafted
tokens, so the sampling cost per step also grows with MTP. Combined, the levers make Qwen3.6 1.8 times faster on real
requests than the stock configuration. For this MoE model two or three drafted tokens perform the same.

## Flint with backend sampling

Flint has no MTP layer. With the CUDA-graphs build at the full 262,144-token context:

| Configuration | Generation (tokens/s) |
|---|---|
| Plain | 22.47 |
| **Backend sampling (`-bs`)** | **24.26 (+8 %)** |

Flint's vocabulary is smaller (150,144 entries) than Qwen's, so CPU sampling cost less to begin with. In both Flint and
Qwen3.6 runs, `-bs` made reading these short prompts slower (e.g. 47 → 23 tokens/s for a 21-token prompt); the absolute
cost is under a second per request.

## What to use

- **MoE models (Qwen3.6, Flint):** a CUDA-graphs build, a Q4_0/Q4_1 file, `-bs`, and for Qwen3.6
  `--spec-type draft-mtp` with the default three drafted tokens.
- **Dense models (Qwen3.8-27B):** a Q4_0 file, a CUDA-graphs build and `--spec-type draft-mtp --spec-draft-n-max 2`
  (or 1); `-bs` is optional.
- On a 4 GB host, add the memory settings from the [setup guide](../setup.md#running-llama-server-on-a-4-gb-host)
  (`--cache-ram 0`, few context checkpoints, `-ub 128` for long contexts).
