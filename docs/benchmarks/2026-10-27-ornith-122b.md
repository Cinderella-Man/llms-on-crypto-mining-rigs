# Ornith-1.5-122B on nine P106 cards: stock llama.cpp and Miner Llama v2.0

*Measured 2026-10-27.*

The first rig run of [Ornith-1.5-122B](../../models/ornith-1.5-122b/README.md), a 122 B-parameter hybrid
mixture-of-experts model that uses about 10 B parameters per token, in a 2–3-bit file that fills the rig's nine 6 GB
cards. It answers four questions: how the model has to be split over the cards, how much context fits, how fast a
coding agent runs on stock llama.cpp with and without the model's multi-token-prediction (MTP) head, and what Miner
Llama v2.0, which was built and tuned on Flint, does with it. A second file, Unsloth's UD-Q2_K_XL, turned out faster on
the rig and closer to the makers' Q8_0: on v2.0 it finished all twelve tasks of the agent check at 2.1 minutes each.

## Setup

| Item | Value |
|---|---|
| Rig | the [reference rig](../mining_rig.md): nine P106-090 6 GB cards, each on a PCIe 1.0 x1 link; a 2-core Celeron with 4 GB of RAM |
| Model file | AtomicChat's [Ornith-1.5-122B-AD-IQ3_XXS-IQ2_S](https://huggingface.co/AtomicChat/Ornith-1.5-122B-GGUF), 47.6 GB: routed experts in IQ3_XXS (down) and IQ2_S (gate, up), 39.6 GB; attention, Gated DeltaNet projections, shared experts, embedding and output layer in Q8_0; the MTP layer in Q4_K |
| Stock engine | llama.cpp `d77256999` (2026-10-22), CUDA 12.9, built for compute capability 6.1 |
| Miner Llama | [v2.0](https://github.com/Cinderella-Man/llama.cpp/releases/tag/miner-llama-v2.0) (`37e717ff6`): the same upstream commit plus this project's changes |
| Loading | from a USB 3 stick that reads 435 MB/s; llama.cpp's memory-mapped loader takes 6 minutes for this file on the Celeron |
| Sampling | the makers' settings: temperature 0.6, top-p 0.95, top-k 20, min-p 0 |

## Fitting it on the cards

- Each of the 48 layers holds ~887 MiB of weights. The 12 full-attention layers keep 2 KiB of KV cache per token each
  (f16); the 36 Gated DeltaNet layers keep a 4 MiB recurrent state per conversation, whatever its length.
- llama.cpp's compute buffer per card grows with context × micro-batch: about `ub × (0.32 MiB + 8 B × context)`.
- **The default split fails.** It puts six layers on five cards, two of them with two attention layers each, and at
  65,536 tokens those two cards run out of memory on the first long prompt.
- **`-ts 5,6,5,6,5,5,6,5,7`** gives each six-layer card exactly one attention layer. llama.cpp counts 50 slots for this
  model: 48 layers, the MTP layer (skipped unless MTP is on) and the output layer; the last two go to the last card.
- **With the MTP head**, its 1.35 GB layer also goes to the last card: `-ts 6,6,5,6,6,5,6,5,5` and `-ub 256`.
- The fullest card then sits at 5,830–5,850 MiB of its 6,068. The host keeps 500–600 MB available and swaps a few
  hundred MB: llama-server keeps up to four context checkpoints in host memory, each a 149 MiB copy of the recurrent
  state.

Largest context per micro-batch, from llama.cpp's own memory projection (`--fit` at the trace log level, which reads
the file's metadata without loading it; [scripts/fit_probe.sh](../../scripts/fit_probe.sh), per card for 16
configurations in [fit_projection.csv](../data/2026-10-27_ornith/fit_projection.csv)) with at least 150 MiB left on
every card:

| Micro-batch (`-ub`) | Largest context, f16 KV cache |
|---|---|
| 512 | 49,152 (run) |
| 256 | ~90k |
| 128 | 122,880 (run; 131,072 leaves only 114 MiB on the last card) |
| 256, with the MTP head | 49,152 (run; 65,536 leaves 83 MiB) |

## A coding agent at work

The [agent check](../../bench/agent_check/README.md): the pi coding agent fixes twelve small bugs (six Python, six
JavaScript, real test runs, five to ten tool calls each), one attempt per task, at most 12 minutes per attempt, and no
attempt starts after 35 minutes. Nine cards, `-c 49152`, the makers' sampling on every request. Generation and prompt
reading in tok/s over every request of the run:

| Engine, line | Tasks done (passed) | Minutes per task, median | Generation | Prompt reading | First token per turn, median |
|---|---|---|---|---|---|
| Stock llama.cpp, `-b 2048 -ub 512` | 7 (6) in 35.5 min | 3.8 | 5.4 | 52 | 10.2 s |
| Stock llama.cpp + MTP head, `-b 2048 -ub 256` | 9 (9) in 43.8 min | 3.1 | 6.6 | 52 | 11.7 s |
| **Miner Llama v2.0**, `-b 2048 -ub 512` | **9 (7)** in 42.6 min | **2.9** | **8.8** | **67** | **8.7 s** |
| Miner Llama v2.0 + MTP head, `-b 2048 -ub 256` | 9 (8) in 35.5 min | 2.5 | 7.9 | 64 | 11.4 s |

- **v2.0 is 1.4× faster per task** than stock on the six tasks both passed (16.9 against 23.6 minutes), and generates
  63 % faster over the session.
- **On v2.0 the MTP head is a wash:** on the seven tasks v2.0 passed without it, 18.1 against 18.6 minutes. It
  finished one more task (list-ops in 5.6 minutes), but generation over the session dropped from 8.8 to 7.9 tok/s, and
  each turn's first token came later (`-ub 256`, the extra layer reading the prompt). Both engines accepted 43 % of the
  head's drafts (up to three per step).
- **The MTP head gives stock 22 % more generation speed but no time per task on these six tasks** (23.7 against 23.6
  minutes): its line needs `-ub 256`, and its extra layer reads every prompt too, so each turn's first token comes
  later. It pays on long answers: with it, stock finished list-ops (8.2 min) and scale-generator (9.9 min), the two
  tasks that ran into the 12-minute cap elsewhere.
- **The failures are long reasoning, not errors:** list-ops ran into the cap on stock and v2.0 while the model worked
  through the exercise's argument order for `foldr`; scale-generator did on v2.0 with and without the head. No tool
  call was malformed in any run; one or two per run failed (the tool returned an error), none on v2.0 without the head.
- **Tool requests:** stock llama.cpp samples them on the CPU (all 31 requests), v2.0 on the cards (none fell back).
- **The harness rates all four lines "Overall: NO-GO", on host memory:** its check asks for at least 600 MB
  available and no swap growth; the 4 GB host kept 421–595 MB available at its lowest and swapped ~300 MB more during
  each run (stock 507 MB, 349 → 653 MB; stock + MTP 482, 369 → 670; v2.0 595, 369 → 696; v2.0 + MTP 421, 354 → 652).
  Its other checks passed, apart from the request count on the tasks cut at the 12-minute cap.
- **GPU energy:** the nine cards draw 270–295 W while tasks run. On the six tasks both passed v2.0 used 80.6 Wh against
  stock's 109.0 Wh (1.35× less): 45 J per generated token against 68 (cards only, `nvidia-smi` every 10 s).
- **Short turns are expensive:** a 30-token tool result still waits ~3.3 s for its first token. Thirty tokens route to
  about 60 % of the 256 experts in every layer, so even a short batch reads ~24 GB of expert weights.
- Commands: [the agent check](../../bench/agent_check/README.md#the-release-check-one-command-1-h), with
  `SAMPLING='{"temperature":0.6,"top_p":0.95,"top_k":20,"min_p":0}'`, `BUDGET_MIN=35`, `TIME_CAP_MIN=12`, `CTX=49152`,
  and the server lines below.

### The same check with Unsloth's UD-Q2_K_XL

[Unsloth's file](#unsloths-ud-q2_k_xl), `-b 2048 -ub 512 -ts 8,6,5,5,5,4,5,6,6` on both engines:

| Engine | Tasks done (passed) | Minutes per task, median | Generation | Prompt reading | First token per turn, median |
|---|---|---|---|---|---|
| Stock llama.cpp | 9 (8) in 38.8 min | 3.5 | 6.2 | 53 | 9.8 s |
| **Miner Llama v2.0** | **12 (12)** in 35.9 min | **2.1** | **9.7** | **67** | **7.6 s** |

- **v2.0 is 1.67× faster per task** than stock on the eight tasks both passed (16.0 against 26.7 minutes), and it is
  the only line on this page that finished all twelve tasks within the budget. Stock's scale-generator ran into the
  12-minute cap.
- **Against the AD file:** on the seven tasks v2.0 passed with both files, 13.7 against 18.6 minutes; on stock's six,
  20.3 against 23.6. Generation over the session: 9.7 against 8.8 tok/s on v2.0, 6.2 against 5.4 on stock. These are
  single runs at temperature 0.6, so per-task minutes also carry the spread of different answers.
- No tool call was malformed; stock had one failed call, v2.0 none. The harness again rates both lines NO-GO on host
  memory only (lowest MemAvailable 564 and 495 MB, swap 356 → 659 and 359 → 660 MB), and stock also on the proxy-row
  count of the task cut at the cap.

## One request at a time

Diagnostics, one llama-server per line, `-bs`: a fresh 13,700-token prompt, the next turn that adds 2,200–2,600 tokens
to it, then 256 generated tokens at 16k of context; and two fresh short prompts at temperature 0.

| Line | Fresh prompt, tok/s | Next turn, first token | Decode at 16k, tok/s | Decode, short prompts, tok/s |
|---|---|---|---|---|
| Stock, `-c 49152 -ub 512` | 182 | 30.2 s | 5.3 | 5.9, 6.2 |
| Stock + MTP head (`--spec-type draft-mtp --spec-draft-n-max 3`), `-c 49152 -ub 256` | 108 | 33.2 s | 8.0 | 7.3, 8.7 |
| Miner Llama v2.0, `-c 49152 -ub 512` | 263 | — | — | — |
| Miner Llama v2.0, `-c 122880 -ub 128` | 181 | 20.6 s | 8.3 | 9.7, 8.9 |

- The MTP head drafts up to three tokens with the model's own extra layer; 41–56 % of drafts were accepted (2.2–2.7
  tokens per step), so stock decodes 23–51 % faster. Prompts read slower, mainly because of the smaller micro-batch its
  memory needs.
- v2.0's `-ub 512` prompt figure comes from the server log of the pipelined-speculation test, which read the prompt
  before it failed. The micro-batch does not change one-token steps, so the `-ub 128` line's decode figures hold for it.
- **The largest context, 122,880 tokens at `-ub 128`, loads and serves:** the fullest card holds 5,907 MiB, and the host
  keeps 844 MB available. This run used 16k of it.

### Unsloth's UD-Q2_K_XL

[UD-Q2_K_XL](https://huggingface.co/unsloth/Ornith-1.5-122B-GGUF) (44.5 GB) keeps the dense tensors smaller (mostly
Q4_K and Q5_K, output in Q6_K) and mixes its routed experts from IQ1_S up to Q8_0 (mostly IQ3_XXS and IQ2_S, then
IQ2_XXS, IQ1_S, IQ2_XS, Q2_K, Q3_K and IQ3_S). Its layers range from 0.58 to 1.06 GB, so the split goes by bytes: `-ts 8,6,5,5,5,4,5,6,6` (llama.cpp's default
split overfills card 5). The fullest card then holds 5,469 MiB, ~400 MiB less than with the AD file. Same probe,
`-c 49152 -ub 512` (its agent check is [above](#the-same-check-with-unsloths-ud-q2_k_xl)):

| Line | Fresh prompt, tok/s | Next turn, first token | Decode at 16k, tok/s | Decode, short prompts, tok/s |
|---|---|---|---|---|
| Stock | 172 | 31.7 s | 6.2 | 6.4, 6.7 |
| Miner Llama v2.0 | 209 | 26.4 s | 8.0 | 10.6, 9.7 |

- Against the AD file, decoding is ~10 % faster on short prompts on both engines and prompts read slower (v2.0: 209
  against 263 tok/s). Its dense tensors read ~1.8 GB less per token (3.8 against 5.7 GB): at ~150 GB/s that is ~12 ms
  of the AD file's ~118 ms, about the 10 % measured. None of its expert types has a Pascal kernel either. The decode at 16k stopped after ~155 tokens, so it is less precise.
- **Quality:** against the makers' Q8_0, UD-Q2_K_XL is closer than the AD file on all three texts tested (mean KL
  divergence / same top token): wikitext 0.184 / 83.5 % against 0.233 / 81.4 %, held-out agent sessions 0.054 / 94.9 %
  against 0.066 / 94.3 %, the agent check's Exercism code 0.071 / 96.3 % against 0.081 / 96.2 %
  ([docs/data/2026-10-27_ornith_kld](../data/2026-10-27_ornith_kld/README.md)).

## Where a token's time goes (Miner Llama v2.0)

v2.0's kernel profiler (`GGML_CUDA_PROFILE`, summarized by [scripts/prof_summary.py](../../scripts/prof_summary.py);
full output in [decode_profile_v2.txt](../data/2026-10-27_ornith/decode_profile_v2.txt)) over ~590 one-token steps: 117.7 ms of GPU time per token summed over the
nine cards (8.5 tok/s if the cards ran back to back), which matches the measured speed.

| Part | ms per token | Share | Read rate per card |
|---|---|---|---|
| Routed experts, gate and up (IQ2_S) | 26.0 | 22 % | ~29 GB/s |
| Routed experts, down (IQ3_XXS) | 24.8 | 21 % | ~19 GB/s |
| Q8_0 dense tensors: attention and Gated DeltaNet projections, shared experts, output layer | 38.7 | 33 % | ~150 GB/s |
| Attention (12 layers) | 7.6 | 6 % | |
| Gated DeltaNet (36 layers) | 4.4 | 4 % | |
| Everything else (norms, router, small ops) | 16.3 | 14 % | |

The Q8_0 tensors already run near a P106's ~179 GB/s on v2.0's Pascal kernels: 160 GB/s for the attention
projections, 169 for the output layer, 90–125 for the small shared-expert products. The routed experts read 1.2 GB per
token at 19–29 GB/s on llama.cpp's own kernels; at 150 GB/s they would take ~8 ms instead of 51, for est. ~13 tok/s.

## Miner Llama v2.0, feature by feature

| v2.0 feature | On Ornith-1.5-122B | How it shows |
|---|---|---|
| CUDA graphs on Pascal, launch shape | work | the server reuses its decode graphs |
| Pascal matrix-vector kernels | work on the Q8_0 tensors: ~150 GB/s | kernel profile |
| Routed experts in IQ2_S / IQ3_XXS | no Pascal kernel: llama.cpp's own, 19–29 GB/s, 43 % of decode time | kernel profile |
| Shared-expert gate/up/GLU fusion | works: one launch per layer | kernel profile |
| Norms that write the Q8_1 row | do not fire (0 norms in every graph) | `GGML_CUDA_NORM_Q8_DEBUG` |
| Persistent MoE kernel | not used: built for Flint's shapes and Q5_0/Q8_0/Q5_K/IQ4_XS experts | no first-use line |
| Prompt attention kernel (compute 6.1) | works at head size 256 with the f16 cache | first-use line; fresh prompt 263 against stock's 182 tok/s |
| GPU sampling for tool requests | works: no request fell back to the CPU | server log |
| Pipelined speculation (`--pipe-depth`) | fails: the request returns HTTP 500 at the first wrong guess | the recurrent state cannot step back; llama.cpp's M-RoPE position check refuses the next batch |
| Card-built attention mask | not tried: off by default, and v2.0 keeps the host mask for M-RoPE models such as Ornith | code |
| `--checkpoint-gen` (agent prompt cache) | not available: it needs a sliding-window model | code |
| MTP head (upstream llama.cpp, also in v2.0) | runs, but gains nothing over v2.0 alone: generation 8.8 → 7.9 tok/s over a session (stock gains 5.4 → 6.6) | agent check; cause not profiled yet (v2.0's Pascal kernels do take the 2–4-token verification batches of the Q8_0 tensors; the experts run on llama.cpp's own kernels in both engines) |

## What v3 needs for Ornith

1. **Pascal kernels for the expert formats.** The routed experts are 43 % of a token and run at a sixth of the card's
   bandwidth. IQ2_S and IQ3_XXS first (this file), then IQ2_XXS, IQ1_S, Q2_K and Q3_K (Unsloth's UD-Q2_K_XL mixes them).
   Est. ~13 tok/s plain, from 8.8. The first IQ2_S/IQ3_XXS kernels (Q166) gave UD-Q2_K_XL +10 % decode at 28–36 GB/s.
   Tuned on a P106 (sign masks in registers, registers for three blocks per SM), they read the fused gate/up at
   6.7–7.3 ps per weight (48–53 GB/s) against llama.cpp's 10.0–11.1, and the expert down at 7.1–9.2 against 17.4–18.7:
   the UD file's IQ2_S/IQ3_XXS expert products take 17.3 ms of GPU time per token against 31.6
   ([data](../data/2026-10-27_iq_kernels/README.md)). Their agent check is next. At 2–4 tokens per call (MTP
   verification) the expert kernels are still slower than llama.cpp's.
2. **The hybrid branch on `pascal-p106-v3`** (Q162: a recurrent-state group per pipe slot, the card-built mask for
   M-RoPE models), so pipelined speculation works. Its state groups (~144 MiB each, nine at depth 3) need memory that
   this file does not leave: it pairs with item 3.
3. **A Pascal-shaped Ornith file.** This file reads 5.7 GB of Q8_0 dense tensors per token; Q6_K or Q5_K there (Pascal
   kernels exist) read 1.3–2.0 GB less per token and free as much card memory for context, the MTP layer or state
   groups; UD-Q2_K_XL's smaller dense tensors already give ~10 % (above). Its quality is checked against the Q8_0
   reference, as both files' are ([docs/data/2026-10-27_ornith_kld](../data/2026-10-27_ornith_kld/README.md)).
4. **The MTP head on v2.0:** it gains 22 % on stock and nothing on v2.0. A profile of the verification step comes
   first; item 1's kernels must take the 2–4-token verification batches too. Pipelined speculation (item 2) is the
   other way to use the idle cards, without the head's 1.35 GB.
5. **Short prompts:** a 30-token turn waits ~3.3 s for its first token while its batch reads ~24 GB of expert weights;
   the expert kernels of item 1 for small batches, not only for one token.
6. **Loading:** 6 minutes through the memory-mapped loader against ~2 minutes at the stick's read speed.

## Where this stopped (2026-10-27)

Done: the agent check on the AD file (four lines) and on UD-Q2_K_XL (stock and v2.0), memory projections, probes,
v2.0's decode profile, both files' quality against the Q8_0, and Pascal kernels for IQ2_S and IQ3_XXS (Q166): correct
on a V100 and a P106, tuned on a P106. Next, in this order:

1. **Attention at ~40k tokens of context** (Q210): one profiled run of Q166's round-1 build on UD-Q2_K_XL with a fresh
   ~40k-token prompt ([run/attn_depth.sh](../data/2026-10-27_iq_kernels/run/attn_depth.sh)), against the same build's
   short-context profile, where FLASH_ATTN_EXT takes 1.1 ms of a 98.8 ms token.
2. **The tuned IQ kernels on the agent check:** Q166's default build (`ea55c7865`) first gives the same output as the
   round-1 build on the two identity prompts (the tuning changes register use, not the arithmetic), then runs the agent
   check on UD-Q2_K_XL (`ud-v3` in [run/agent_ornith.sh](../data/2026-10-27_ornith/run/agent_ornith.sh)), against
   v2.0's 12/12 at 2.1 minutes per task.
3. **A Q5_0 output layer** in both files: KL divergence against the Q8_0 first, then the agent check.
4. **Expert kernels for 2–8 tokens** (Q211), so that the MTP head and pipelined speculation pay.
5. **Kernels for UD-Q2_K_XL's other expert types** (IQ2_XXS, IQ1_S, IQ2_XS, Q2_K, Q3_K, IQ3_S: 27 % of its expert
   bytes), and the hybrid branch (Q162) for pipelined speculation.

## Commands

Stock llama.cpp and Miner Llama v2.0 take the same line (the release archives unpacked in `llama-p106-v2.0/`).
UD-Q2_K_XL:

```bash
llama-p106-v2.0/llama-server -m Ornith-1.5-122B-UD-Q2_K_XL.gguf -ngl 99 -fa on -c 49152 -np 1 -b 2048 -ub 512 -ts 8,6,5,5,5,4,5,6,6 -bs --ctx-checkpoints 4 --cache-ram 0 --jinja --reasoning-format deepseek --temp 0.6 --top-p 0.95 --top-k 20 --min-p 0 --host 127.0.0.1 --port 8080
```

AD-IQ3_XXS-IQ2_S:

```bash
llama-p106-v2.0/llama-server -m Ornith-1.5-122B-AD-IQ3_XXS-IQ2_S.gguf -ngl 99 -fa on -c 49152 -np 1 -b 2048 -ub 512 -ts 5,6,5,6,5,5,6,5,7 -bs --ctx-checkpoints 4 --cache-ram 0 --jinja --reasoning-format deepseek --temp 0.6 --top-p 0.95 --top-k 20 --min-p 0 --host 127.0.0.1 --port 8080
```

With the MTP head: `-ub 256 -ts 6,6,5,6,6,5,6,5,5 --spec-type draft-mtp --spec-draft-n-max 3` instead of
`-ub 512 -ts 5,6,5,6,5,5,6,5,7`.
