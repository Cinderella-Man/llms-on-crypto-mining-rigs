# 10. v3: one build, three models

> **In short**
> - v3 took Qwen3.8-Flash-Next from 7.8 to 20.75 tokens per second for a coding agent, in three days, on the same rig
>   with no new parts.
> - No single change did it. Kernels for the model's shapes, smaller messages between cards, a cheaper draft head and
>   cards held at their full clock each added a part.
> - Every feature is behind its own switch, and each model gets a preset: the switches and the command line it was
>   measured with.
> - Flint and Ornith-1.5-122B run on the same build at their old speed or better.
> - Testing the release turned up two bugs in upstream llama.cpp itself.

Facts in this chapter are from 2026-11-05. The release build is fork branch `pascal-p106-v3-b12076-ladder5`.

## 10.1 Where v3 started

On 2026-11-03 Flash-Next ran on the rig for the first time ([chapter 9](09-the-models.md)). With v2.0's code a coding
agent got 7.8 tokens per second, and a token took about 136 ms of GPU time across the nine cards. Almost a third of
that went to BF16 matrices, a format Pascal cards have no fast path for. The weights a token reads would take about
24 ms at the cards' memory speed ([chapter 2](02-how-an-llm-makes-text.md)), so most of the time was not reading
weights at all. It was overhead: launches, waiting, and hops between cards.

## 10.2 The steps

| Date | What changed | Tokens written per second | Bugs fixed |
|---|---|---|---|

| 2026-11-03 | the slowest weights converted to a format the cards read faster | 9.0 | 12 of 12 |
| 2026-11-04 | the MTP draft, guessing three tokens ahead, with its memory fixed | 12.2 | 11 of 12 |

| 2026-11-04 | the same with the MTP draft and its shortlist head | 16.0 | 12 of 12 |
| 2026-11-04 | newer kernel shapes and the 8-bit hop | 18.8 | 12 of 12 |
| 2026-11-05 | the same line on the second rig, the control for the next step | 19.19 | 12 of 12 |
| 2026-11-05 | the keep-alive | **20.75** | **12 of 12** |

The rows ran on two identical rigs and several builds, so two rows far apart are not one clean comparison. Each step
has its own controlled comparison in its data folder.

The kernel work is [chapter 6](06-gpu-code.md): Pascal code for BF16 and 2-bit weights, and kernels that read each
weight once for several tokens. With them and a newer upstream base, a token went from ≈136 ms to ≈75 ms. The draft is
[chapter 8](08-guessing-ahead.md). The three stories below are the newest steps.

## 10.3 Story: cards that slow down while they wait

**The idea.** On a layer split only one card works at a time: card 1 runs its layers, hands the state to card 2, and
waits. With nine cards, each one is busy for roughly a ninth of every ~50 ms token (my estimate). NVIDIA's
driver sees a card that is mostly idle and lowers its clock. When the state arrives, the card starts its next slice slow. If something kept
every card busy, the driver would keep the clock up.

**How it should work.** One tiny GPU program per card, one thread, on the card's lowest-priority stream. It reads a word
in host memory in a loop and ends when the word changes. It uses almost nothing, but the card never looks idle, and the
real work always runs ahead of it. Think of a keep-alive packet that stops a load balancer from closing a quiet
connection.

**What I did.** The switch `GGML_CUDA_KEEPALIVE` starts the loop after each graph on a card and ends it before anything
that must wait for the card to be empty: a free, a new pinned buffer, a graph capture. `decode` runs it while the model
decodes, `request` also wakes every card when a request arrives, and `idle` keeps it running for 120 s after the last
token.

**What happened.** The clock log showed every card at 1,354 MHz while decoding without it, and at 1,873 to 1,911 MHz
with it. A plain token took 51 ms instead of 60 to 63, 14 to 19 % less. On the agent check, with the draft, generation
went from 19.19 to 20.75 tokens per second and prompts read 12.5 % faster; every task passed in both arms. The cards
draw 5 to 11 % more energy per token. `request` was no better than `decode`. `idle` was worse: under CUDA's lazy loading
the first launch of each kernel waited behind the 120 s loop, and the session's first request waited 506 s for its
prompt.

**Why.** A GPU's power manager guesses the work ahead from the work just done. A layer split looks like a card that is
idle most of the time, so the guess is wrong for every card, all the time. The loop changes what the driver sees, not
what the model does: the tokens are the same.

## 10.4 Story: a smaller message between cards

**The idea.** At each of the eight card boundaries the model's state crosses the host over PCIe 1.0 x1 ([chapter
5](05-nine-cards.md)). Flash-Next's state is 40,960 bytes in 32-bit floats. In 8-bit Q8_0 it is about a quarter of that.

**What happened.** The bytes alone predicted a saving of 0.33 ms per boundary, 2.6 ms a token. Measured without a draft,
the 8-bit hop through a pinned host ring went from 14.98 to 17.06 tokens per second, 8.1 ms a token: three times the
prediction. The KL divergence against 32-bit hops showed no measurable change.

**Why.** The new path saves more than bytes. The staged hop also replaces host-side work between the cards with one
copy into a ring the next card reads. The prediction counted only the wire. This is the lesson of
[chapter 3](03-measuring.md) again: an estimate tells you whether to try, and only the measurement tells you what you
got.

## 10.5 Story: a draft that stopped paying, and a cheaper head

**The puzzle.** On v3's base the MTP draft took Flash-Next from 7.8 to 12.2 tokens per second. On the new kernels, the
same draft gave 14.6 against 14.3 without it: almost nothing.

**Why.** A token now took about 68 ms. A step of three drafted tokens and a four-token check cost about what its ~2.1
accepted tokens saved. Once the main model got cheaper, the draft's own cost mattered. Most of that cost is its output
head: a score for each of 248,320 tokens, for every guess.

**What I did.** `LLAMA_DRAFT_SHORTLIST` runs the draft's head over a shortlist of likely tokens, with an exact bound
that falls back to the full head when the shortlist might miss the best one. The guesses are the same, and they are
still checked by the main model.

**What happened.** 16.0 tokens per second against 14.6, with the same acceptance (0.705 against 0.697), and 12 of 12
tasks. The draft paid again.

## 10.6 Every feature behind a switch

By v3 the fork changed upstream in close to a hundred places (88 run-time switches today), built on many branches. I put every one into one
build, each behind a switch, with its default the engine's own behaviour: features that help stay on, experiments stay
off. Setting a switch to its other value gives upstream's path for that one change.

This does three things. A user can turn off any one change if it misbehaves on their model. I can measure each change
on its own, in one binary, on the rig. And small gains don't get lost: a change that saves 1 % is kept behind its
switch, tested with the other small ones as a group, instead of being thrown away for being small. A hundred 1 %
gains are a large gain.

The check that makes this safe: with every switch at its default, the build gives the earlier build's logits bit for
bit on every architecture llama.cpp's test suite builds, 143 of 143. The whole list is [docs/switches.md](../switches.md).

## 10.7 One preset per model

The switches that help one model can hurt another, or need a quality check first. The 8-bit hop passed its check on
Flash-Next, but Flint and Ornith have not had theirs. So each model gets a preset, `release/<model>-v3/settings.env`:
the switches and the command line its own agent check ran with. One command starts it.

| Model | Preset | Tokens written per second, coding agent |
|---|---|---|
| [Qwen3.8-Flash-Next](../../release/flash-next-v3/README.md) | `pmix-q2-fast`, the MTP draft with the shortlist head, the 8-bit hop, the keep-alive | 20.75 |
| [Flint](../../release/flint-v3/README.md) | v2's command line, no switch | 45.9 (v2: 44.6–45.9) |
| [Ornith-1.5-122B](../../release/ornith-v3/README.md) | my valid1 file, no switch | 14.9 (before: 14.5) |

## 10.8 Story: a test that failed one time in three

**What happened.** The release build's GPU check failed one of its 4,759 expert cases: an expert product with 2,561 rows, a shape
no release model has. The same case had passed on the build before. It looked like a new bug.

**What I did.** I ran the case 30 times on each build. It failed 23 times on the new build and 19 times on the old one.
The earlier pass was luck. The cause is in upstream llama.cpp's own code: for one token through the expert path, the
matrix-vector kernel bounds its rows by the output's stride, which spans every expert. When the row count is not a
multiple of the rows a block handles, each expert's last block writes into the next expert's output.

**Why it matters.** A single passing run proves little when a failure is a race. I patched it in upstream's style on
upstream's `master`, where new test cases failed 30 of 30 and 29 of 30 runs before the fix and 0 of 80 after
([Cinderella-Man/llama.cpp#1](https://github.com/Cinderella-Man/llama.cpp/pull/1)). The release build carries the
fix. A second upstream bug, in how speculative decoding restores its random draws after a checkpoint, came out of an
earlier statistical test ([#2](https://github.com/Cinderella-Man/llama.cpp/pull/2)). Both are written up for anyone
to check in [docs/upstream_fixes.md](../upstream_fixes.md).

## 10.9 Flint and Ornith on the new build

Flint Q8_0 ran the agent check at 45.9 tokens per second with v2's command line, 12 of 12, the top of v2.0's range.
Ornith-1.5-122B in my valid1 file ran at 14.9, 12 of 12, against 14.5 for the same file a week earlier.

One thing changed: at temperature 0, Flint's tokens leave v2.0's after 60 to 133 tokens on four test prompts. Each
time it happens at a token where the two best choices were close, so a small change in the order of additions picks
the other one. Upstream's own changes since v2.0's base are under the build. Whether the model's distributions moved
is a KL-divergence measurement against v2.0: TODO(kld).

## What to remember

- Flash-Next went from 7.8 to 20.75 tokens per second for a coding agent through many changes of about 8 to 35 % each.
- On a layer split the cards wait most of the time, and the driver slows them down for it. Keeping them busy with a
  near-empty loop gave 8 % on the agent check.
- A prediction from bytes alone missed most of the hop's saving: the host work between cards mattered more.
- A faster main model makes a draft's own cost matter; making the draft cheaper brought its gain back.
- Every feature behind a switch, and a preset per model, keeps each change measurable and keeps small gains.
- A test that passes once may still fail one time in three. Run it many times.
