# Large ("stretch") MoE models and MoE-specific compression for 9 × P106-090 (54 GB in nine 6 GB pools)

Research date: 2026-10-22. Scope: MoE models of roughly 40B–150B+ total parameters that might be squeezed into ~45–50 GB of VRAM, the compression techniques that get them there (low-bit GGUF, expert pruning/merging, MoE-aware quant mixes), and inference-time MoE tricks. Options only; no winner is picked.

How the numbers were collected (applies to every section):
- Model lists, `config.json` architecture fields, licences, repo-creation dates and **exact GGUF file sizes** come from the Hugging Face Hub API (`/api/models/...`, `/api/models/<repo>/tree/main`) and raw `config.json` files, read on 2026-10-22. HF "created" = repo-creation date, which can precede the public release by weeks (e.g. Mistral-Small-4-119B-2603 repo created 2026-01-23, released 2026-03). File sizes are in decimal GB (10^9 bytes); multi-part GGUFs are summed; `mmproj` vision files are excluded.
- **Per-layer tensor sizes** are my own analysis: I read only the GGUF header (tensor index: names, shapes, types, offsets) of each file via HTTP Range requests and computed each tensor's byte size from consecutive offsets. No weight data was downloaded. Sizes in this analysis are MiB/GiB (2^20/2^30).
- **Rig budget used in fit analysis:** 9 × 6068 MiB = 54,612 MiB = 53.3 GiB = 57.3 GB (decimal). A "48 GB" GGUF file is therefore about 44.7 GiB.
- Everything labelled **claim to test** is not verified on this hardware.

## 1. Which MoE models between ~40B and ~150B+ total parameters exist as of October 2026, and what are their architectures?

### Takeaway
There are far more candidates than in mid-2025. The 2026 additions in range are Qwen3.5-122B-A10B (and fine-tunes such as Ornith-1.5-122B), Qwen3-Coder-Next 80B-A3B, Qwen3.8-Flash-Next (125B core + 51B n-gram embedding table), Mistral Small 4 119B-A6.5B, Laguna-S-2.1 118B-A8B (poolside), Ling-2.6/3.0-flash (107B/124B), Nemotron 3 Super 120B-A12B and Nemotron 3.5 Bolt 74B-A9B, LongCat-Flash-Lite 68.5B, Jamba2-Mini 52B, plus many REAP/REAM-pruned versions of 200–300B models (Step-3.5-Flash, MiniMax-M2.x) that land at 121–172B. The architectures differ a lot in KV-cache cost: hybrid linear-attention models (Qwen3.5/Next/3.8, Ling-3.0, Kimi-Linear, Nemotron) need ≤24 KiB of f16 KV per token. Full-GQA models need far more: GLM-4.5-Air 184 KiB, MiniMax-M2 248 KiB, and dots.llm1 about 1 MiB per token. That matters as much as file size on 6 GB cards.

### Inferences
- On a rig where each GPU has ~6 GB and context costs VRAM on every card, the hybrid linear-attention families (Qwen3.5/Next/3.8, Ling-3.0, Nemotron, Kimi-Linear, Jamba) and MLA models (Mistral Small 4, LongCat) leave the most room for weights. GLM-4.5-Air/4.6V, MiniMax-M2 REAPs, Hunyuan and Phi-3.5-MoE pay 128–248 KiB per token. dots.llm1 is effectively ruled out by KV alone (≈1 MiB/token means 32k context ≈ 31 GiB).
- At full precision, Qwen3.6-35B-A3B roughly matches Qwen3.5-122B-A10B on the coding/agent benchmarks shown (SWE-bench V 73.4 vs 72.0; Terminal-Bench 2.0 51.5 vs 49.4; LCB 80.4 vs 78.9). The 122B leads on knowledge/reasoning (MMLU-Pro 86.7 vs 85.2; HLE 25.3 vs 21.4). So the "stretch" 122B case rests more on knowledge breadth and robustness than on headline coding scores. These are cross-card comparisons that may use different harnesses.

### Gaps
- Active-parameter counts for gpt-oss-120b, Ling-flash-2.0, Phi-3.5-MoE, dots.llm1 and Jamba2-Mini were not re-verified from primary pages.
- MiniMax-H3 (2026-07-28) config was not accessible (404); its unsloth GGUF totals only 20.1 GB, so it may be small or partial. Not investigated.
- No independent leaderboard (LMArena / Artificial Analysis) values were collected for most models; the AA page did not show comparators.
- llama.cpp support for Nemotron Bolt's per-layer heterogeneous expert counts, Qwen3.8's n-gram tables and Ling-3.0's KDA layers on CUDA/Pascal is inferred from arch strings and existing GGUFs, not tested.

## 3. Per-layer fit on nine separate 6 GB pools (layer split)

### Takeaway
For most candidates no single layer is anywhere near 6 GB. The largest layers found are 1.4–2.3 GiB: GLM-Air's MTP layer, Ling-3.0's last layer, Jamba, Nemotron Bolt and LongCat MoE blocks. So the real constraints are the **sum per GPU**, the **output tensor and compute buffer on the last GPU**, and **KV on every GPU**. Qwen3.5-122B quants up to UD-IQ3_S (46.6 GB) and ubergarm IQ2_KL (46.5 GB) pack into nine GPUs at 32k–64k context with ~200–500 MiB to spare per GPU under my assumptions (UD-IQ2_M leaves ~1.1 GiB). GLM-4.5-Air at UD-IQ2_XXS fits only to ~32k, and MiniMax-REAP-139B IQ2_M only to ~16k, because of KV. Nemotron Bolt and LongCat have the most uneven layers.

- llama.cpp lets you place individual tensors on chosen devices with `-ot/--override-tensor <regex>=<buffer type>`. It splits layers proportionally with `-ts/--tensor-split`, and `-sm/--split-mode` offers `none, layer (default; layers and KV, pipelined), row, tensor (experimental)` — [llama.cpp common/arg.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp) (master, 2026-10-22).
- ik_llama.cpp's own examples use `-sm graph` for multi-GPU offload. - Whether GLM's MTP ("nextn") layer occupies VRAM in mainline is unclear. llama.cpp now has an MTP context type that uses the nextn layer(s) for drafting ([llama-model.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model.cpp), lines around "LLAMA_CONTEXT_TYPE_MTP"), and mainline MTP speculative decoding was merged in May 2026 (PR #22673) — [aiweekly summary](https://aiweekly.co/alerts/llamacpp-adds-multi-token-prediction-for-faster-local-ai), [mer.vin guide](https://mer.vin/2026/05/run-qwen-3-6-mtp-in-llama-cpp-faster-local-inference-with-built-in-speculative-decoding/). **Claim to test**: GLM-4.5-Air loads the 1.4 GiB MTP layer to the GPU when MTP is not used.

### Inferences
- The hidden state that crosses each GPU boundary is n_embd × 4 bytes per token (12 KiB for Qwen3.5-122B), so PCIe 1.0 x1 (~190 MB/s) adds roughly 0.5 ms per token across 8 boundaries in generation. In prompt processing it adds ~30 ms per boundary per 512-token batch (arithmetic, not measured). Splitting a layer's experts onto another GPU via `-ot` adds hops of the same size, so fine-grained balancing is cheap in bandwidth terms but adds synchronisation steps.
- llama.cpp's default `-ts` splits by layer count or free memory, not by actual layer bytes. With uneven layers (Bolt, GLM's dense first and MTP last layers, Ling-3.0's last layer, Jamba), the default split can overflow one GPU while others have room. Manual `-ts` or `-ot` per-layer device maps are likely needed near the limit.
- Qwen3.5-122B at UD-IQ3_XXS (864 MiB/layer) puts 6 layers per GPU (≈5.1 GiB weights), i.e. 8 GPUs for 48 layers. The 9th GPU then holds output.weight (597 MiB) and slack. So uniform layers waste little.
- The 300 MiB compute-buffer assumption is the softest number here. Lowering `-ub` (e.g. 128) shrinks buffers at some prompt-speed cost. This must be measured on the rig.

### Gaps
- Actual llama.cpp CUDA compute-buffer sizes per GPU for each of these architectures on Pascal, and the CUDA context overhead outside the 6068 MiB figure.
- How llama.cpp places LongCat's n-gram tables (arch absent upstream) and Qwen3.8's n-gram/PLE tables. Embedding-type tensors are class `LLM_TENSOR_LAYER_INPUT` (CPU) in [llama-arch.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-arch.cpp), but whether qwen4exp's 51B-parameter table is in that class was not confirmed.
- Per-layer analysis was done for one or two quants per model. Other uploaders' recipes (e.g. bartowski Q3_K_XL) can change the layer pattern.

## 4. Quality data for low-bit MoE quants, and whether a big MoE at ~2.5–3 bpw beats a smaller MoE at Q6/Q8

### Takeaway
Within one model, perplexity loss for good MoE quants is small down to ~3.3–3.8 bpw for Qwen and GLM (+1–5%), but Step-3.5-Flash is already +15% at 3.3 bpw. At 2.0–3.4 bpw the loss grows: +6–20% for Qwen3.5-122B and Qwen3-Coder-Next (3.05→2.06 bpw), +11–27% for GLM-4.5-Air (3.41→2.80 bpw), and +76% for Step-3.5-Flash at 2.35 bpw. Sensitivity is strongly model-dependent. Task benchmarks sometimes disagree with PPL/KLD (Unsloth reports their IQ2_XXS beating another uploader's IQ3_S on LiveCodeBench/MMLU-Pro). For "big-low-bit vs small-high-bit", the evidence points both ways. Older dense studies and vendor results (DeepSeek-V3.1 at 2–3 bit; NVIDIA Bolt 2-bit vs Qwen3.6-35B) favour the big model. But Qwen3.6-35B-A3B at full precision already matches Qwen3.5-122B-A10B on coding benchmarks, and no direct same-memory head-to-head for these models was found.

### Inferences
- At the ~43 GiB budget that fits this rig, Qwen3.5-122B sits at ~3.0 bpw (IQ2_KL, +5.9% PPL) or the Unsloth UD-IQ3_XXS mix. Qwen3-Coder-Next fits at 4–5 bpw (≤+1% PPL), and Qwen3.6-35B-A3B fits at Q8 with lots of room. Given Qwen3.6-35B ≈ Qwen3.5-122B on coding at full precision, a 3-bit 122B would have to lose almost nothing to win on coding. Its likelier advantages are knowledge, long-tail robustness and instruction following. This is a hypothesis to test, not a finding.
- PPL deltas are not comparable across models. Step-3.5-Flash's large jump at 2.35 bpw suggests not every 100B+ MoE tolerates 2-bit, so each candidate needs its own check (KLD against a high-precision reference) before committing disk and time.

## 5. Expert pruning and merging (REAP, REAM, EAN, HC-SMoE, GSQ-RCO): quality retained, available checkpoints and GGUFs, domain pruning, DIY feasibility

### Takeaway
REAP (Cerebras, arXiv 2510.13999, ICLR 2026) is the dominant one-shot method. At 25% expert removal it typically keeps coding within ~1–3 points and sometimes improves agentic/tool scores. At 40–50% it loses more, especially on multiple-choice and knowledge (MC avg −13% at 50%). It needs domain-matched calibration: C4-only calibration collapses coding. REAM (Samsung SAIL Montreal, arXiv 2604.04356) merges low-saliency experts into REAP-chosen centroids and slightly beats REAP at 25% on Qwen3-30B, Qwen3-Next-80B and Qwen3-Coder-Next. An independent 2026 benchmark (MoEXBench) found pruning costs much more PPL than Q4 quantisation (+27% PPL at 20% pruning on its reference model). There are many in-range pruned checkpoints with GGUFs: GLM-4.5-Air-REAP-82B, Step-3.5-Flash-REAP-121B/149B, MiniMax-M2.5/M2.7-REAP-139B, Qwen3.5-122B REAP-20/30, Qwen3-Coder-Next REAP/REAM-60B and community 48B, Qwen3-Next-80B-REAP-60B, gpt-oss-120b-REAP-58B, Nemotron-3-Super-64B-Math-REAP, and Qwen3.8-Flash-Next REAP/GSQ-RCO variants. DIY REAP on a separate, more powerful PC on the same LAN (a "workstation") looks feasible in principle with Cerebras' 2026 layer-wise observer; whether it works depends on that machine's GPU VRAM and system RAM.

### Cited Findings
**REAP method and paper results**
- Saliency S_j = mean over tokens routed to expert j of g_j(x)·‖f_j(x)‖₂. Lowest-scoring experts are pruned, and averaging only over active tokens protects rare specialists — [REAP paper arXiv 2510.13999v2](https://arxiv.org/html/2510.13999v2).
- Qwen3-30B-A3B baseline / REAP 25% / 50%: Eval+ 0.814 / 0.797 / 0.780; LiveCode 0.302 / 0.304 / 0.302; WildBench 0.811 / 0.804 / 0.718; MC avg 0.721 / 0.665 / 0.503. GLM-4.5-Air: Eval+ 0.786 / 0.759 / 0.679; LiveCode 0.374 / 0.412 / 0.352; MC avg 0.747 / 0.674 / 0.554 — [paper](https://arxiv.org/html/2510.13999v2).
- Qwen3-Coder-480B: SWE-bench Verified 0.540 / 0.540 / 0.522 at 0/25/50%. Kimi-K2 (W4A16): 0.554 / 0.580 / 0.576. Mean generative-coding drop excluding large models is 1.9% at 25% and 6.9% at 50%. Merging (HC-SMoE, M-SMoE) loses >5% on coding at 25% and >20% at 50%. Frequency pruning collapses at 50% (Qwen3-Coder-480B code avg 0.010). EAN is close to REAP at 25% and on tool use, but behind at 50% on coding (GLM-Air 0.487 vs 0.515). Merging causes "functional subspace collapse" (up to 100× contraction) in high-granularity MoEs — [paper](https://arxiv.org/html/2510.13999v2).
- Calibration: ≤110B models used 1,024 samples packed to 2,048 tokens. C4-only calibration collapses code accuracy, sometimes to 0% — [paper](https://arxiv.org/html/2510.13999v2).
- REAP code: a memory-efficient layer-wise (block-wise) calibration observer for pruning large models on a single GPU was added 2026-03-30, and a March 2026 fix renormalises top-k router logits in the saliency calculation — [CerebrasResearch/reap](https://github.com/CerebrasResearch/reap) (per search snippet, 2026-10-22; not read in full).

**Independent evidence on pruning cost and composition**
- MoEXBench: REAP on an unnamed reference model (bf16 weights): PPL 6.82 → 8.67 at 20% (+27%), 10.04 at 30% (+47%), 15.81 at 50% (+132%). Q4_K_M weights plus Q8 KV add only 0.1–0.4 PPL on top. The paper recommends BF16 REAP as the default path and treating calibration data as a hyperparameter — [arXiv 2608.21693](https://arxiv.org/html/2608.21693v1).
- A REAP-pruned Kimi K3 IQ1_S card warns Chinese, Japanese and other languages will be degraded, "likely severely" — [hellohazime/Kimi-K3-REAP640-IQ1_S-GGUF](https://huggingface.co/hellohazime/Kimi-K3-REAP640-IQ1_S-GGUF) (via search snippet).

### Inferences
- At equal file size on this rig, the head-to-head options are: Qwen3.5-122B UD-IQ3_XXS (44.75 GB, ~3.1 bpw over 122B) vs REAP-30 88B at IQ4_XS (47.12 GB, ~4.3 bpw) vs REAP-20 99B at IQ3_M (43.70 GB); and GLM-4.5-Air UD-IQ2_XXS (42.68) vs GLM-4.5-Air-REAP-82B Q3_K_M (42.88). MoEXBench suggests pruning hurts PPL more than going from Q4 to Q3. REAP's own tables suggest 25% pruning barely moves coding/agentic scores. Both could be true: PPL over general text versus code-calibrated task scores.
- Code-calibrated REAP or domain-directed pruning (GSQ-RCO Coder, Samsung's 0.7-code mix) fits a coding/agent use case but likely sacrifices multilingual and general knowledge. The Kimi K3 warning and REAP's MC-average drops support that.
- DIY REAP for Qwen3.5-122B on the workstation would need the BF16 checkpoint (ubergarm lists BF16 at 227.5 GiB ≈ 244 GB, so the workstation needs a few hundred GB of free disk), the REAP repo's layer-wise observer, a calibration set (~1k × 2k tokens of code/agent data), then GGUF conversion, imatrix and quantisation, all on the workstation. Feasibility depends on the workstation's GPU VRAM and system RAM.

### Gaps
- No published benchmarks for the Qwen3.5-122B REAP-20/30, Qwen3-Next-REAP, gpt-oss-REAP-58B, MiniMax-M2.5-REAP-139B or Nemotron-Math-REAP checkpoints beyond what is cited above.
- No PPL/KLD comparison of a REAP GGUF against an unpruned GGUF of equal size was found.
- REAP/REAM interaction with Unsloth/ubergarm-style low-bit mixes (e.g. does pruning make the remaining experts more quantisation-sensitive?) is unmeasured.

## 6. Inference-time MoE tricks that trade quality for speed

### Takeaway
Two practical knobs exist in llama.cpp-family engines. Mainline has a static expert-count override via `--override-kv <arch>.expert_used_count=int:N`, with no runtime flag (a feature request was closed "not planned"). ik_llama.cpp has `-ser Kmin,t` "Smart Expert Reduction", which on DeepSeek-Lite gave 5–12% generation speed-ups for ~1–2% PPL loss. On this rig the payoff is limited for models whose non-routed weights dominate per-token reads. For Qwen3.5-122B UD-IQ3_XXS, attention/DeltaNet/shared/output are 4.24 GiB of the 5.39 GiB read per token, so going from 8 to 4 experts cuts only ~11% of bytes. Hunyuan-A13B, MiniMax-REAP and Qwen3-Next gain more. Lossless speed-ups via MTP/DFlash speculative decoding are now in mainline (MTP, May 2026). Training-free adaptive top-k research shows only small gains (≈5%).

### Cited Findings
- `--override-kv nemotron_h_moe.expert_used_count=int:8` was confirmed working by the reporter of llama.cpp issue #19528 ("--expert-override flag for MoE models", opened 2026-02-11). Maintainer CISC pointed to the generic `--override-kv <arch>.expert_used_count=int:N`. No dedicated flag was added; the issue closed 2026-03-28 as not planned. The reporter found 4–6 experts adequate for chat and 8–10 better for long-context summarisation on Nemotron-3-Nano (informal) — [llama.cpp #19528](https://github.com/ggml-org/llama.cpp/issues/19528).
- GGUF metadata keys (my header read) for the override: `qwen35moe.expert_used_count=8`, `qwen3next…=10`, `glm4moe…=8`, `mistral4…=4`, `laguna…=10`, `step35…=8`, `minimax-m2…=8`, `bailingmoe2/3…=8`, `hunyuan-moe…=8`, `llama4…=1`, `phimoe…=2`, `kimi-linear…=8`, `longcat-flash-ngram…=12`. The NVIDIA Bolt GGUF carries no single `expert_used_count` key in my read (its expert counts are per layer) — GGUF headers of the repos in section 2.
- ik_llama.cpp SER (PR #239, 2025-03-01): always use the top Kmin experts, and use experts Kmin..K only if p_i > t·p_0; `-ser Kmin,1` equals a fixed Kmin. On DeepSeek-Lite (6 active experts, IQ4_NL) Kmin=5 at t=1 raised PPL error from the 0.8% quantisation baseline to 1.36%. The author recommends Kmin=4,t=0.2 or Kmin=5,t=0.4 for 5–7% TG gain, and reports ~12% TG gain at Kmin=4,t=0.4 with ~1.6% error on an RTX-4080. He notes that on CUDA, fewer experts beats skimping on attention-tensor bits. Not implemented on Metal — [ik_llama.cpp PR #239](https://github.com/ikawrakow/ik_llama.cpp/pull/239).
- Community "fewer experts" finetune-by-config: DavidAU's Qwen3-30B-A1.5B sets 4 of 128 experts active with "no loss of function" in informal testing and recommends ≥8 experts for IQ1/IQ2 quants; no PPL/KLD given — [DavidAU model card](https://huggingface.co/DavidAU/Qwen3-30B-A1.5B-64K-High-Speed-NEO-Imatrix-MAX-gguf); expert count can also be set per request via `num_experts_used` per DavidAU's guide — [DavidAU guide](https://huggingface.co/DavidAU/How-To-Set-and-Manage-MOE-Mix-of-Experts-Model-Activation-of-Experts).
- Training-free adaptive top-k: elbow-based routing (arXiv 2608.04401, ICLR 2026 workshop) cuts latency 5.3% on OLMoE with accuracy maintained. SMIDT (AAAI 2026) is a dynamic-top-K serving framework (1.05–3.13× throughput, pipeline-parallel setting) — [arXiv 2608.04401](https://arxiv.org/pdf/2608.04401), [SMIDT](https://ojs.aaai.org/index.php/AAAI/article/view/39403).
- Layer removal: `llama-quantize --prune-layers L0,L1,...` ("comma-separated list of layer numbers to prune… WARNING: advanced option") exists in mainline — [tools/quantize/quantize.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/quantize.cpp). No quality data for MoE layer pruning was found.
- Speculative decoding: mainline MTP merged in May 2026 (PR #22673; `--spec-type draft-mtp`); reported speed-ups range from 1.5–1.8× to ~2× (single-user Strix Halo report: Qwen3.6-27B 6.2 → 29.8 t/s) — [aiweekly](https://aiweekly.co/alerts/llamacpp-adds-multi-token-prediction-for-faster-local-ai), [sleepingrobots](https://sleepingrobots.com/dreams/mtp-qwen36-strix-halo). Unsloth publishes [Qwen3.5-122B-A10B-MTP-GGUF](https://huggingface.co/unsloth/Qwen3.5-122B-A10B-MTP-GGUF) (2026-05-15). NVIDIA ships DFlash "LiLiCorr" drafters for Bolt ([card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-BF16)), and poolside's fork has DFlash for Laguna ([card](https://huggingface.co/poolside/Laguna-S-2.1)).
- Mainline also has `--moe-cache-mib N` ("GPU cache size in MiB for the MoE experts kept in the CPU… split among [GPUs] like the layers") — [common/arg.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp); a third-party post says it was merged in early October 2026 with a 2.2× decode speed-up on an RTX 5090 — [developersdigest](https://www.developersdigest.tech/blog/llama-cpp-moe-offload-n-cpu-moe-vs-moe-cache-2026).

### Inferences
- For Qwen3.5-122B, the highest-leverage speed knob is probably the precision of attention/DeltaNet/shared tensors (Q6_K in UD-IQ3_XXS, Q5_K in UD-IQ2_M, iq6_k in ubergarm IQ2_KL), not the expert count. That runs opposite to ik's DeepSeek-Lite finding and is specific to this model's high non-routed share. For Hunyuan, MiniMax-REAP and Step-REAP, expert reduction could cut bytes by 20–40%.
- Speculative decoding on MoE verifies several tokens per pass, which touches more distinct experts per layer, so speed-ups may be smaller than on dense models. Pascal decode uses MMVQ for 1–8 columns (ik doc below), so draft lengths ≤7 stay on the MMVQ path. **Claim to test.**
- `--moe-cache-mib` is designed for experts in host RAM. With 4 GB of host RAM, experts kept "on the CPU" would page from disk and run CPU matmuls on a non-AVX Celeron, or be copied to the GPU over PCIe x1 (≈20 ms per ~4 MB expert). It is unlikely to help except as a curiosity for models slightly over 54 GB.

### Gaps
- No measured PPL/KLD/benchmark data for expert-count reduction on Qwen3.5-122B, Qwen3-Next, GLM-Air, Laguna or Mistral-4.
- Whether `-ser` works with the hybrid architectures (qwen35moe, qwen3next) in ik_llama.cpp, and on Pascal.
- MoE layer-skipping quality data.

## 7. MoE-aware quant mixes (high-precision attention/router/shared/embeddings, low-bit routed experts) and imatrix

### Takeaway
All serious uploaders already use MoE-aware mixes: attention/SSM/shared experts at 5–8 bits, routed `ffn_down_exps` at ~3 bits and `ffn_gate/up_exps` at ~2–2.6 bits. The DIY tooling exists: mainline `llama-quantize --tensor-type` and `--tensor-type-file`, and ik's `--custom-q` regex recipes. Unsloth's Qwen3.5 study names `ssm_out` and `ffn_down_exps` as the most sensitive tensors and attention tensors as sensitive in hybrids, and finds gate/up experts fine at 3 bits. Imatrix helps most at low bits, but rarely routed experts get sparse calibration, a known MoE problem.

### Cited Findings
- Mainline `llama-quantize` options include `--tensor-type tensor_name=ggml_type` ("quantize this tensor to this ggml_type… may be specified multiple times", e.g. `--tensor-type attn_q=q8_0`), `--tensor-type-file`, `--output-tensor-type`, `--token-embedding-type`, `--pure`, `--imatrix`, `--prune-layers` — [tools/quantize/quantize.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/quantize.cpp) (master 2026-10-22).
- ubergarm's Qwen3.5-122B IQ2_KL recipe (ik `--custom-q`): attention/gated-DeltaNet tensors (attn_gate, attn_qkv, attn_q/k/v, attn_output, ssm_alpha, ssm_beta, ssm_out) at iq6_k; shared experts iq6_k; routed `ffn_down_exps` iq3_ks; routed `ffn_gate/up_exps` iq2_kl; token_embd iq4_k; output iq6_k. Result: 43.319 GiB, 3.047 bpw, PPL +5.9% — [ubergarm card](https://huggingface.co/ubergarm/Qwen3.5-122B-A10B-GGUF). The recipe comment says "60 repeating layers", apparently copied from the 397B recipe (the 122B has 48).
- Actual Unsloth mixes read from GGUF headers (2026-10-22): Qwen3.5-122B **UD-IQ3_XXS** = attention/DeltaNet/shared Q6_K, routed gate/up **IQ2_S**, down **IQ3_XXS**. **UD-IQ2_M** = attention Q5_K, gate/up IQ2_XXS, down IQ3_XXS. **UD-Q2_K_XL** = attention Q5_K, gate/up IQ2_XS, down IQ3_XXS, shared Q6_K. Mistral-Small-4 UD-IQ3_XXS = MLA projections Q8_0/Q6_K, fused gate_up IQ2_S, down IQ3_XXS (32 layers) / IQ4_XS (4 layers), shared Q6_K. GLM-4.5-Air UD-Q2_K_XL = attention mostly Q4_K, gate/up Q2_K, down IQ4_NL (35) / Q5_0 (11), shared Q5_1/Q8_0. NVIDIA Bolt 24GB = experts and shared IQ2_XXS, attention Q8_0 — repos in section 2. So an "IQ3_XXS" or "Q2_K_XL" label says little about the routed-expert bits.
- Unsloth sensitivity findings (Qwen3.5): `ssm_out` and `ffn_down_exps` are most sensitive (ssm_out at q2_k is much worse for little saving). Any `attn_*` tensor is especially sensitive in hybrid architectures. `ffn_up_exps`/`ffn_gate_exps` are generally fine at 3-bit. ~IQ3_XXS for FFN tensors is the best size/99.9%-KLD trade-off. Imatrix reduces KLD/PPL most at low bits but I-quants run 5–10% slower. Their llama.cpp speed table shows iq3_xxs/iq2_xxs tg ≈85.7 t/s vs ≈90–91 t/s for k-quants on their GPU — [Unsloth Qwen3.5 GGUF benchmarks](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks).
- APEX (LocalAI/mudler): a role-based MoE mix (routed experts compressed hardest, shared/attention kept higher, edge layers higher) with "I" variants using a chat/code/reasoning/tool-call imatrix corpus. Output is a standard GGUF that works in stock llama.cpp. Self-reported on Qwen3.5-35B-A3B: F16 64.6 GB PPL 6.537; APEX Quality 21.3 GB PPL 6.527; APEX Mini 12.2 GB PPL 7.088 — [LocalAI blog](https://localai.io/blog/apex-moe-quantization/).
- ik's SER PR argues that on CUDA, keeping attention/shared at 5–8 bits and using fewer experts beats `--pure` low-bit attention — [ik PR #239](https://github.com/ikawrakow/ik_llama.cpp/pull/239).
- MoE calibration: rarely activated experts receive insufficient calibration data, leading to poor quantisation parameters. EAQuant oversamples under-activated experts — [EAQuant arXiv 2506.13329](https://arxiv.org/html/2506.13329v3). LLM Compressor forces all experts to see calibration tokens to avoid miscalibration or NaNs — [vLLM llm-compressor docs](https://docs.vllm.ai/projects/llm-compressor/en/0.10.0/examples/quantizing_moe/). ubergarm publishes his calibration corpus — [gist](https://gist.github.com/ubergarm/edfeb3ff9c6ec8b49e88cdf627b0711a).

### Inferences
- A rig-specific custom mix is within reach on the workstation. Start from BF16/Q8 GGUF; keep attention/DeltaNet/shared at Q6_K or Q5_K (Q5_K saves ~0.5 GiB/token read on Qwen3.5-122B vs Q6_K); routed down IQ3_XXS; gate/up IQ2_S/IQ2_XS. Size it so each 6-layer block fills about 5.3–5.5 GiB per GPU, using a code/agent imatrix. Because KV is small for Qwen3.5, the spare ~0.5 GiB per GPU could go to bits instead of context.
- For ik-only types (IQ2_KL, IQ3_KS, IQ1_KT), CUDA kernel coverage on sm_61 is the deciding risk (section 8 open questions).

### Gaps
- llama.cpp-specific handling of experts with no imatrix data (warnings, fallback behaviour) was not verified in source.
- No controlled study isolating "attention at Q8 vs Q5" on a hybrid MoE was found, beyond Unsloth's qualitative sensitivity notes.

## 8. Experiment ideas and open questions

### Takeaway
The experiments below are options, not a plan. The cheapest first steps need no disk workaround (≤25 GB files: Nemotron Bolt 24GB, Qwen3-Coder-Next IQ2-class or REAP-60B IQ3_XXS). The "stretch" tests (Qwen3.5-122B ~3 bpw, GLM-Air REAP vs quant, Mistral-4, Laguna, Step/MiniMax REAPs) need network storage served from the workstation (NFS) or an external disk for the 35–48 GB files. Pascal-specific engine behaviour (flash attention, ik quant kernels, a CPU without AVX) is the main technical risk.

### Cited Findings
- ik_llama.cpp Pascal/Volta doc (commit 3dbc2c9f8, 2026-10-13). With f16 or q8_0 KV, flash attention runs on the GPU on P40/GTX 10xx-class sm_61 for head size 128 (Qwen3 MoE, GLM-4.5-Air, MiniMax-M2), head size 256 (Qwen3.5, Qwen3.6, Qwen3-Next) and head size 64 (gpt-oss; but with a q8_0 cache, generation runs on the CPU). CUDA graphs are not used below Ampere. CUDA 13 dropped Pascal, so use 12.x (NVIDIA recommends 12.9 with the 580 driver branch) — [ik_llama.cpp docs/pascal-volta.md](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/pascal-volta.md), [PR #2670](https://github.com/ikawrakow/ik_llama.cpp/pull/2670).

### Gaps
**Open questions**
- Does mainline llama.cpp's flash attention for head size 256 (Qwen3.5/Next) run fully on the GPU on sm_61, as ik's doc says for ik? Does Mistral-4/LongCat MLA force CPU fallback on mainline too?
- Do ik_llama.cpp's IQ_K/KS/KL/KT quant kernels run on sm_61 (MMVQ/MMQ coverage), and does ik's CPU side (token_embd get_rows for iq4_k, any FA fallback) work at all on a CPU without AVX?
- Real per-GPU compute-buffer sizes, and the best `-ub`/`-b` for 9-way layer split over PCIe 1.0 x1.
- Whether GLM's MTP layer and Qwen3.5's MTP layer are loaded into VRAM when MTP is not used, and how much VRAM MTP drafting costs when it is.
- How the qwen4exp n-gram/PLE tables and LongCat's n-gram embeddings are placed (CPU/mmap vs GPU), and whether 4 GB of host RAM plus disk paging is workable for per-token lookups.
