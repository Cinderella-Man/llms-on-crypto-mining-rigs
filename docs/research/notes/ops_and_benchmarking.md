# Operations and benchmarking methodology for testing many MoE models and engines on the 9 × P106-090 rig (as of 2026-10-22)

Scope: how to store, move, swap and load GGUF models and engine builds given the rig's tiny disk and
RAM; how to build Pascal (sm_61) engines on a separate, more powerful PC on the same LAN (a
"workstation"); how to measure speed and quality
fairly and cheaply; experiment tracking; and a closing list of experiments and baseline-protocol
options. Options are presented, no winner is picked.

Conventions used below:
- "accessed 2026-10-22" means a living document (GitHub `master`, docs site) read on that date; its
  content can change.
- **Claim to test** marks anything unverified, estimated, or measured by someone else on other hardware.
- Rig facts quoted as "hardware spec" come from the measured [hardware spec](../../mining_rig.md),
  not from the web; facts marked "measured on the rig" were read on the rig on 2026-10-22.

Key rig numbers that drive everything below (hardware spec + measurements on the rig): SSD ~485 MB/s
sequential read, ~26 GB free of 64 GB; 4 GB single-channel RAM (3.7 GiB usable), ~1.1 GiB used at idle
with GNOME/Xorg, a 3.7 GiB swap file; CUDA 12.9.2; AES-NI present (SSE4.2, no AVX/AVX2/FMA); gigabit Ethernet
(~112–118 MB/s payload ceiling); host→GPU pinned copies ~189 MB/s for one GPU at a time (GPU4 ~200
MB/s), ~715 MB/s total with all nine in parallel; "filling all nine (54 GB) takes about 80 s even
with transfers in parallel"; 75 W power limit per card (adjustable 60–75 W), ~5 W idle; 83 °C
thermal target.

## 1. Model storage, transfer, and where the rig reads models from

### Takeaway
The rig cannot hold most of the planned GGUFs locally (26 GB free vs 12–50 GB files), so every
option is a trade-off between (a) copying one model at a time over gigabit (~2 min per 12 GB, ~7.5 min
per 50 GB), (b) reading directly from a network mount, (c) a USB 3.0 SSD, or (d) a bigger internal
SSD and/or more RAM. A key, untested insight: current llama.cpp loads tensors in one sequential loop,
so with layer split the load is probably capped by a single GPU's ~190 MB/s PCIe 1.0 x1 link, not by
the 485 MB/s SSD. If that holds, an NFS mount at ~113 MB/s costs ~1.7× the load time of local SSD
rather than ~4×, which makes "no local copy at all" much more viable than it first looks.

### Cited Findings

**Load path inside llama.cpp (what actually limits load time)**
- Load modes: llama.cpp folded the separate mmap/mlock/direct-I/O flags into `-lm, --load-mode
  <auto|none|mmap|mlock|mmap+mlock|dio>` (default `auto`); llama-bench exposes the same `-lm` flag and
  a CSV/JSON column `use_direct_io` — [llama-bench README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md); [llama-server README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). The refactor is listed as "args: refactor mlock/mmap/directio into load-mode (#20834)" in a release note — [newreleases.io b10105](https://newreleases.io/project/github/ggml-org/llama.cpp/release/b10105) (merge date not shown). Older `--mmap/--no-mmap` and `-dio` are documented as deprecated in favour of `--load-mode` — [completion README mirror (gitcode)](https://gitcode.com/SparkLLM/llama.cpp/blob/master/tools/completion/README.md). Implication: scripts must use different flags for older builds and forks (ik_llama.cpp may still use `--no-mmap`/`-mmp`) — **claim to test** per engine with `--help`.
- In `llama-model-loader.cpp` (master, accessed 2026-10-22): `auto` selects mmap when mmap is supported; direct I/O is used only for `LLAMA_LOAD_MODE_DIRECT_IO`. The async upload path uses `n_buffers = 4` staging buffers of 1 MiB (larger when direct-I/O alignment applies) and is disabled when `use_mmap || check_tensors`; it needs device caps `async`, `host_buffer` and `events`. Tensors are processed in one `for (struct ggml_tensor * cur : tensors)` loop; the code does not parallelize uploads across devices. In the mmap path, tensors are copied with `ggml_backend_tensor_set(cur, data, 0, n_size)` from the mapping, and mapped ranges are released with `unmap_fragment` once loading completes — [llama-model-loader.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model-loader.cpp) (read via raw URL; details not checked line by line against the source — **claim to test**).
- The async non-mmap upload path originated in PR #7896 ("Implement non-mapped async IO for CUDA on Windows"), whose author reported ">3x" faster load on a Gen5 NVMe drive — [semanticdiff view of commit 6a2f0b34](https://app.semanticdiff.com/gh/ngxson/llama.cpp/commit/6a2f0b3474d479bda4ac2ee7cfd5dcdcf0be1f79).
- Direct I/O history: in January 2026 direct I/O was switched off by default (PR #19109) after users reported higher RAM use / OOM kills — [semanticdiff PR #19109](https://app.semanticdiff.com/gh/ggerganov/llama.cpp/pull/19109/overview). An open PR (#20461, approved 2026-04-02) fixed llama-bench enabling mmap and direct I/O together — [semanticdiff PR #20461](https://app.semanticdiff.com/gh/ggml-org/llama.cpp/pull/20461/overview). Record the load mode with every benchmark.
- Community discussion "Mmap faster than direct I/O for MoE models" (2026-01-11 to 2026-09-06): repeat loads with O_DIRECT took "at least 10x longer" when the model fits in RAM (mmap keeps it in page cache so repeat runs "load in seconds"); a network share was called "the most pathological case" for direct I/O; gpt-oss-120b reportedly failed to load without `--no-direct-io`. No maintainer comments — [llama.cpp discussion #18758](https://github.com/ggml-org/llama.cpp/discussions/18758).
- A user with an RPC setup reported `llama-server` hanging at `load_tensors` for >100 GiB models while llama-bench worked; `-dio` fixed it (ROCm/Strix Halo, single report) — [llama.cpp issue #19745](https://github.com/ggml-org/llama.cpp/issues/19745).
- Secondary troubleshooting guidance: "filesystem doesn't support mmap (some network shares)" as a cause of "failed to mmap"; suggested fix is copying to local disk — [RunLocalAI error page](https://www.runlocalai.co/errors/llama-cpp-failed-to-mmap) (secondary, **claim to test** on NFS/SMB/SSHFS).

**Transfer over gigabit**
- NFSv4.2 with `rsize=1048576` from a Linux server reached ~113 MB/s on gigabit in one forum report (FreeBSD server: ~80 MB/s until tuned) — [FreeBSD forums, NFS performance](https://forums.freebsd.org/threads/nfs-performance.98574/post-709093). One anecdote, but it is line rate.
- For sequential NFS reads, client read-ahead matters more than rsize; many distros set read-ahead ≈ 15 × rsize but some use 128 KiB; check `/sys/class/bdi/<dev>/read_ahead_kb` and measure with `nfsiostat` — [Google Cloud NetApp Volumes: Linux NFS read-ahead](https://docs.cloud.google.com/netapp/volumes/docs/connect-clients/linux-nfs-read-ahead); same advice for kernels ≥ 5.4 — [Microsoft Learn: NFS performance](https://learn.microsoft.com/en-us/azure/storage/files/nfs-performance). `nconnect` is presented as a throughput scaler for multi-connection links (Azure context) — same Microsoft page; unlikely to matter on one saturated gigabit link (no direct test found).
- rsync over SSH can be CPU-bound on weak hosts: the SSH cipher, not the network, limited throughput in older reports; a lighter cipher (`-e "ssh -T -c aes128-ctr -o Compression=no -x"`) gave ~3.37 Gbit/s on a fast host; rsync's own daemon protocol avoids encryption entirely on a trusted LAN — [TrueNAS forum](https://www.truenas.com/community/goto/post?id=547468); [Atomic Object: rsync speedup on underpowered systems](https://spin.atomicobject.com/rsync-speedup-on-underpowered-systems/) (older posts; Arcfour advice is obsolete). A report of rsync failing on large files when `--compress` is combined with resumed transfers — [Launchpad list](https://lists.launchpad.net/aims/msg01654.html). GGUF weights are near-incompressible, so compression only costs CPU.
- Hugging Face CLI: `hf` replaces the deprecated `huggingface-cli`; `--local-dir` works with `hf download`; Xet-backed repos need the `hf_xet` package or fall back to slower HTTP ("Xet Storage is enabled for this repo, but the 'hf_xet' package is not installed") — HF forum threads via search-result snippets (exact thread for each quote not confirmed): [Strange problem with huggingface-cli](https://discuss.huggingface.co/t/strange-problem-with-huggingface-cli/160083), [Downloading files](https://discuss.huggingface.co/t/downloading-files/176662); slow downloads without the xet package reported in [xet-core issue #407](https://github.com/huggingface/xet-core/issues/407). huggingface-hub 1.23.0 added dual progress bars (download + reconstruction) for Xet transfers in `hf download` — [newreleases.io huggingface-hub 1.23.0](https://newreleases.io/project/pypi/huggingface-hub/release/1.23.0). Resume behaviour/flags not confirmed from a primary source (**check `hf download --help`**).
- `llama.cpp/scripts/` contains `hf.sh` and `verify-checksum-models.py` helpers — [llama.cpp scripts dir, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/tree/master/scripts) (contents not inspected).

**USB 3.0 SSD on the rig**
- UAS needs host controller, enclosure and kernel support; some USB–SATA bridges (e.g. a JMicron JMS561U adapter) are blacklisted for UAS and silently fall back to slower `usb-storage` (BOT) — [kernel bugzilla 201421](https://bugzilla.kernel.org/show_bug.cgi?id=201421). Check the active driver with `lsusb -t` ("driver=uas" vs "usb-storage"); quirks can be forced with `usb-storage.quirks=` — [Manjaro forum](https://forum.manjaro.org/t/usb-connected-external-ssd-uas-errors-and-possible-quirks-fix/185768/5). No throughput benchmark was found for USB 3.0 UAS reads (the commonly quoted ~400+ MB/s is a **claim to test** with `fio`/`dd`).

**Bigger internal SSD (LUKS) and more RAM**
- Growing an encrypted install: grow partition → `cryptsetup resize` → `pvresize` → `lvextend -r`, outermost layer inward — [Arch Wiki: Resizing LVM-on-LUKS](https://wiki.archlinux.org/title/Resizing_LVM-on-LUKS); [Ubuntu community wiki: ResizeEncryptedPartitions](https://help.ubuntu.com/community/ResizeEncryptedPartitions). Clonezilla "proportional" cloning worked for one LUKS install — [Fedora discussion](https://discussion.fedoraproject.org/t/howto-clone-a-luks-encrypted-install-to-a-bigger-disk/125753); a plain `dd` copies the old partition table, which must then be fixed. One Ubuntu user's grown LUKS root dropped to BusyBox ("vgubuntu-root" not found), so initramfs/crypttab must be checked before reboot — [Ubuntu Discourse](https://discourse.ubuntu.com/t/need-help-with-boot-after-running-out-of-space-in-luks-volume-copying-to-larger-hard-drive/75327).
- The rig's RAM can be expanded to 32 GB via the free slot; the two Celeron cores and 4 GB single-channel RAM are described as a bottleneck for CPU work — [hardware spec](../../mining_rig.md).

### Inferences
- **Load-time model (claim to test).** If uploads are sequential and each tensor goes to one GPU (layer split), effective load ≈ min(storage, one GPU's PCIe ≈ 190 MB/s pinned, possibly less for pageable mmap copies). Then: 40 GB from local SSD ≥ ~210 s (3.5 min); from NFS at ~113 MB/s ≈ 355 s (6 min); from a page-cached file it is still ~210 s. The hardware spec's "54 GB in ~80 s" applies only to deliberately parallel uploads, which the stock loader does not do. A parallel-per-GPU loader would be the only way to approach the ~715 MB/s aggregate; no engine was found that does this (gap).
- **LUKS may be an unmeasured bottleneck.** On the tested install the root FS is dm-crypt (LUKS2, aes-xts). The Celeron has AES-NI (measured on the rig), so decryption is hardware-accelerated, but on 2 cores the decrypt throughput could still fall below the 485 MB/s raw read. Whether the 485 MB/s figure was measured through LUKS is not stated. `cryptsetup benchmark` on the rig would settle it (read-only, safe). A non-encrypted USB SSD or NFS mount would bypass dm-crypt entirely.
- **SSH encryption may cap transfers.** rsync-over-SSH at ~112 MB/s needs the Celeron to decrypt ~1 Gbit/s on one core. Options: `-c aes128-gcm@openssh.com` (hardware-accelerated, since the Celeron has AES-NI) or `chacha20-poly1305@openssh.com`, `-o Compression=no`, rsync daemon mode, or NFS (no encryption, kernel path). **Claim to test:** `openssl speed -evp aes-128-gcm` and a timed 5 GB transfer.
- **Copy-based workflow option.** Keep the library on the workstation (`/models/<repo>/<file>.gguf` + a `SHA256SUMS`/manifest). Push one model at a time: `rsync -a --partial --inplace --info=progress2 -e "ssh -c <fast cipher> -o Compression=no" src rig:/srv/models/`. `--inplace` avoids a second temporary copy when replacing a file of the same name (matters with 26 GB free); `--partial` keeps a resumable partial file. Delete the previous model first. Integrity: compare against Hugging Face's LFS sha256 on the workstation once; on the rig, rsync's built-in whole-file checksum on transfer is a cheaper check than re-hashing 40 GB on two Celeron cores (rsync ≥ 3.2 checksum negotiation is known behaviour, not checked against a primary source).
- **Mount-based workflow options** (no copy, no rig disk use):
  - NFS (read-only export of the workstation's model dir, `vers=4.2,rsize=1048576,ro,noatime`, raised read-ahead): kernel client, no encryption, lowest CPU; works with mmap on Linux in general but must be tested with llama.cpp's mmap and `-lm none` paths. Probably the simplest.
  - SMB/CIFS: similar idea, more CPU and less mmap predictability (no source found).
  - SSHFS: FUSE + SSH encryption on the Celeron — likely the slowest and most CPU-heavy (no source; claim to test).
  - NBD / iSCSI: export a read-only ext4 image of the model library as a block device; the rig sees a local-looking disk, page cache behaves normally, no per-file protocol overhead. More setup; no llama.cpp-specific reports found.
  - With only 4 GB RAM, nothing large stays in page cache, so every load re-reads the file from the network; mmap vs `-lm none` vs `-lm dio` should be measured, and `dio` over a network share is reported as pathological (above).
- **USB 3.0 SSD option.** A 1–2 TB USB SSD formatted ext4 (unencrypted unless desired) holds a rotating subset of the library; read speed (likely PCIe/USB-bridge-limited at a few hundred MB/s) would exceed the ~190 MB/s single-GPU upload cap, so load time could match the internal SSD. Confirm UAS with `lsusb -t`. Cheapest hardware change, fully reversible, no LUKS work.
- **Internal SSD upgrade option.** A 512 GB–1 TB M.2 SATA drive removes the space problem but requires a clone + LUKS/LVM grow (or reinstall) with someone at the keyboard, and buys little load speed if the PCIe cap is real. Highest effort, highest risk of an unbootable system.
- **RAM upgrade option.** A 2nd DDR4 SO-DIMM (e.g. 16 GB → 20 GB total, or 2 × 16 GB) gives dual channel and room for page cache: repeat loads of a ≤ ~25 GB model would come from RAM, which mainly helps the NFS/USB/LUKS-bound cases. It also leaves headroom for engines that allocate host buffers and for `-ncmoe` experiments (though CPU expert compute on 2 SSE-only cores will be very slow). Cheap and reversible; needs a power-down (and, on a LUKS install like the tested one, the passphrase at the keyboard at boot).

### Gaps
- No published measurement of llama.cpp load time from NFS/SMB/SSHFS/NBD on gigabit, nor of mmap vs `-lm none` on a 4 GB-RAM host with a fully offloaded multi-GPU model.
- Whether any engine/fork uploads to several GPUs in parallel during load (none found).
- Real UAS throughput of USB 3.0 SSDs on this board; the actual dm-crypt decrypt rate with AES-NI on two cores, and whether 485 MB/s was measured through dm-crypt.
- `hf download` resume semantics and checksum verification options from a primary source.

## 2. Building engines for Pascal (sm_61) on the workstation

### Takeaway
Build inside `nvidia/cuda:12.9.2-devel-ubuntu24.04` (CUDA 12.9.2 and glibc 2.39 = the rig's), with explicit
`CMAKE_CUDA_ARCHITECTURES=61`, `GGML_NATIVE=OFF` **and** every x86 SIMD option above SSE4.2 forced OFF
(non-native builds otherwise default AVX/AVX2/FMA/F16C/BMI2 on and will SIGILL on the no-AVX Celeron),
`GGML_CUDA_NCCL=OFF`, and dynamic linking against the CUDA 12.9 libraries already in
`/usr/local/cuda-12.9/lib64` on the rig — or a fully static build if self-contained tarballs matter
more than size. Builds need no GPU in the container when the architecture is explicit.

### Cited Findings
- Official images: `nvidia/cuda:12.9.1-devel-ubuntu24.04` (last updated 2025-07-25, ~5.68 GB compressed amd64) and `12.9.2-devel-ubuntu24.04` (last updated 2026-05-20, ~5.68 GB); `-runtime-` (~2.44 GB) and `-base-` (~138 MB) variants exist for both — [Docker Hub tags API, accessed 2026-10-22](https://hub.docker.com/v2/repositories/nvidia/cuda/tags?name=12.9&page_size=100). The `latest` tag is deprecated (search-result snippets of NGC/Docker Hub pages).
- glibc is only backward compatible: a binary built against newer glibc will not load on older; Ubuntu 24.04 ships glibc 2.39; fix = build in a container matching the oldest target; check with `objdump -T <bin> | grep GLIBC_` and `ldd --version` — [SSD Nodes: portable Linux binaries](https://www.ssdnodes.com/learn/portable-linux-binaries-glibc-musl).
- CUDA 13 dropped offline compilation for Maxwell/Pascal/Volta; ggml's default architecture list includes `61-virtual` only `if (CUDAToolkit_VERSION VERSION_LESS "13")` (comment: "61 == Pascal, __dp4a instruction") — [ggml-cuda CMakeLists.txt, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/CMakeLists.txt). With `GGML_NATIVE=ON`, CUDA ≥ 11.6 and CMake ≥ 3.24 the default is `native` (needs a visible GPU) — same file. A docker/model-runner issue reports recent default builds omitting Pascal and causing "no compatible GPU found" — [docker/model-runner #929](https://github.com/docker/model-runner/issues/929).
- `build.md`: `-DGGML_NATIVE=OFF` for portable builds, `-DCMAKE_CUDA_ARCHITECTURES="…"` to override, `CMAKE_CUDA_COMPILER` + `CMAKE_INSTALL_RPATH`/`CMAKE_BUILD_WITH_INSTALL_RPATH=ON` for a specific toolkit, `-DBUILD_SHARED_LIBS=OFF` for static, ccache recommended; runtime env `CUDA_VISIBLE_DEVICES`, `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1`, `GGML_CUDA_P2P`, `CUDA_SCALE_LAUNCH_QUEUES` — [llama.cpp build.md, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).
- ggml CPU options: `GGML_SSE42`, `GGML_AVX`, `GGML_AVX2`, `GGML_BMI2`, `GGML_FMA`, `GGML_F16C` are "derived from GGML_NATIVE; off in native builds"; AVX-512/AMX/AVX-VNNI default OFF; `GGML_CPU_ALL_VARIANTS` ("build all variants of the CPU backend (requires GGML_BACKEND_DL)"); `GGML_BACKEND_DL` ("requires BUILD_SHARED_LIBS"); `GGML_STATIC` (static link); `GGML_CCACHE` default ON — [ggml/CMakeLists.txt, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/ggml/CMakeLists.txt).
- ggml CUDA options and defaults: `GGML_CUDA_FORCE_MMQ` OFF, `GGML_CUDA_FORCE_CUBLAS` OFF, `GGML_CUDA_NO_PEER_COPY` OFF, `GGML_CUDA_NO_VMM` OFF, `GGML_CUDA_FA` ON, `GGML_CUDA_FA_QUANTS` = `q4_0-q4_0;q8_0-q8_0;f16-f16;bf16-bf16` (or `all`; `GGML_CUDA_FA_ALL_QUANTS` deprecated alias), `GGML_CUDA_GRAPHS` (listed default OFF), `GGML_CUDA_NCCL` ON, `GGML_CUDA_COMPRESSION_MODE` "size" (CUDA ≥ 12.8) — same file and [build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).
- Linking: default (`GGML_STATIC` off) links `CUDA::cudart` and `CUDA::cublas` dynamically (cuBLAS pulls in cuBLASLt at runtime); `GGML_STATIC` on Linux links `cudart_static`, `cublas_static`, `cublasLt_static`; `CUDA::cuda_driver` (libcuda from the driver) is linked unless `GGML_CUDA_NO_VMM`; NCCL is linked when `GGML_CUDA_NCCL` is on and NCCL is found — [ggml-cuda CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/CMakeLists.txt).
- A June/Aug 2026 write-up: benchmarking a binary compiled for the wrong SM made the driver JIT PTX at runtime (52.8 → 62.5 tok/s, pp 106 → 348 tok/s after a correct native build); `GGML_NATIVE=OFF` to avoid baking host CPU features; `GGML_CUDA_NCCL=OFF` on single-GPU hosts; the devel-container build then failed in the slim runtime container with `libnccl.so.2` missing; verify the architecture in startup logs rather than trusting tok/s — [Ian Paterson, "Why Your llama.cpp Benchmarks Are Wrong", 2026-06-06, updated 2026-08-15](https://ianlpaterson.com/blog/llama-cpp-build-from-source-cuda-benchmark/).
- A Tesla P40 (sm_61) user on 2026-02-01 reported recent llama.cpp working well (~20 t/s on small MoE); their build info showed `CUDA : ARCHS = 610`, `FORCE_MMQ = 1`, `USE_GRAPHS = 1`, `FA_ALL_QUANTS = 1` — [llama.cpp discussion #19248](https://github.com/ggml-org/llama.cpp/discussions/19248).
- An issue titled "CUDA: Pascal DP4A MMQ config uses I=64 for Q8_0; I=128 gives +12% pp512 on sm_61" exists — [llama.cpp issue #30235](https://github.com/ggml-org/llama.cpp/issues/30235) (title only seen; **claim to test**). Pascal-specific kernel tuning is still moving.
- ik_llama.cpp: a P100 (sm_60) user built with CUDA 12.9 and `-DCMAKE_CUDA_ARCHITECTURES=60` after upgrading CMake (3.25.1 had C++20 issues) — [ik_llama.cpp discussion #1563](https://github.com/ikawrakow/ik_llama.cpp/discussions/1563). No Pascal-specific "not supported" error was found. On a V100 that was running sm_61 PTX, ik-llama-server aborted on the first flash-attention call (host chose a WMMA path with no matching device kernel) — [llama-swap issue #1185, 2026-09-27/28](https://github.com/mostlygeek/llama-swap/issues/1185). Lesson: always compile real SASS for the exact target (sm_61) rather than relying on PTX JIT.
- llama-swap's unified CUDA 12 Docker image was built with `CMAKE_CUDA_ARCHITECTURES="60;61;75;86;89"` (70 added on 2026-09-28) and bundles llama-server and ik-llama-server — [llama-swap issue #1185](https://github.com/mostlygeek/llama-swap/issues/1185); [llama-swap README, accessed 2026-10-22](https://github.com/mostlygeek/llama-swap).

### Inferences
- **The SIGILL trap.** Per the ggml table, the x86 SIMD options default *on* when `GGML_NATIVE=OFF` (they are "off in native builds" because native detection takes over). So a portable build must pass explicitly: `-DGGML_NATIVE=OFF -DGGML_AVX=OFF -DGGML_AVX2=OFF -DGGML_FMA=OFF -DGGML_F16C=OFF -DGGML_BMI2=OFF -DGGML_AVX512=OFF -DGGML_SSE42=ON` (the 3865U has SSE4.2 but no AVX). **Claim to test:** run `objdump -d libggml-cpu.so | grep -c ymm` (should be 0) and a quick CPU-only `llama-cli` smoke test on the rig. Alternative: `-DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON -DBUILD_SHARED_LIBS=ON` builds several CPU variants and picks one at runtime — test that the SSE4.2/x64 variant is chosen on the Celeron.
- **Candidate configure line (llama.cpp mainline):** `cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=61 -DGGML_CUDA_NCCL=OFF -DGGML_NATIVE=OFF <SIMD flags above> -DLLAMA_CURL=OFF -DCMAKE_INSTALL_PREFIX=/opt/engines/llama.cpp-<shortsha>-<tag> -DCMAKE_INSTALL_RPATH='$ORIGIN/../lib' -DCMAKE_BUILD_WITH_INSTALL_RPATH=ON`. Variants worth building as separate artifacts: `GGML_CUDA_FORCE_MMQ=ON`, `GGML_CUDA_GRAPHS=ON/OFF`, `GGML_CUDA_FA_QUANTS=all` (needed to benchmark q8_0/q4_0 mixed KV-cache types; costs compile time). Single-arch builds should compile much faster than the default multi-arch list.
- **Container recipe option:** `docker run --rm -u $(id -u) -v $PWD/src:/src -v $HOME/.cache/ccache-cuda129:/ccache -e CCACHE_DIR=/ccache nvidia/cuda:12.9.2-devel-ubuntu24.04 bash -c "apt-get install -y cmake ninja-build ccache git && cmake … && cmake --build build -j\$(nproc) && cmake --install build"`. No `--gpus` needed because arch detection is off. Pin the image by digest. The 12.9.2 image matches the rig's installed CUDA 12.9.2 (cuBLAS 12.9.2.10, cudart 12.9.79, measured on the rig); check with `ldd` on the rig that `libcublas.so.12` and `libcudart.so.12` resolve.
- **Linking options:**
  - Dynamic (default): tarball contains only `bin/` + `lib/libggml*.so libllama.so` (small, likely tens of MB), resolving `libcudart.so.12`, `libcublas.so.12`, `libcublasLt.so.12` from the rig's `/usr/local/cuda-12.9/lib64` (via `ld.so.conf.d` entry or `LD_LIBRARY_PATH` in the systemd unit/llama-swap `env`). Requires no CUDA package change on the rig. Check with `ldd` on the rig.
  - Fully static (`GGML_STATIC=ON`, `BUILD_SHARED_LIBS=OFF`): self-contained except for libcuda (driver); binaries will be much larger because cuBLAS/cuBLASLt static libs are huge (size **claim to test**); multiple builds multiply that size on a tiny disk.
  - Bundling the CUDA `.so` files inside each tarball: self-contained but duplicates several hundred MB per build (cuBLASLt alone is large) — likely the worst fit for 26 GB free.
- **Side-by-side builds on the rig:** versioned dirs `/opt/engines/<engine>-<date>-<shortsha>-<flagtag>/` with a `current` symlink per engine, plus a `BUILDINFO.json` (git sha, cmake cache dump, container image digest, nvcc version). With dynamic linking, a dozen builds should fit in well under 1 GB. Alternatively, keep builds on the workstation and run them directly from the NFS mount (binaries are small; startup reads are trivial).
- **Smoke test on the workstation:** a build containing only sm_61 SASS will not run on a modern workstation GPU such as an sm_120 card. Adding `61-virtual` PTX would let the workstation GPU JIT it (catches link/missing-lib errors early) but PTX-path behaviour can differ (cf. the ik_llama WMMA abort) — treat workstation runs as "does it start", never as performance or correctness evidence for the rig.
- **Docker-on-the-rig option** (e.g. llama-swap unified CUDA 12 image, which compiles sm_61 natively): avoids building, but multi-GB images on a 26 GB-free disk and installing nvidia-container-toolkit on the rig (a package change to the rig) make it a poor fit; image sizes and GPU-arch lists change upstream.
- **Rig-built binary as reference:** the tested rig's own native build (llama.cpp commit 85d5703a3, 2026-09-04) is the parity reference; a workstation build at the same commit should give identical tokens (same seed, greedy) and the same t/s within noise.

## 3. Model swapping, serving, and freeing RAM/VRAM (headless)

### Takeaway
Two practical swap layers exist: llama-swap (a Go proxy that starts/stops arbitrary server commands on
demand, one model at a time by default) and llama-server's own router mode (`--models-dir`,
`--models-max`, `--models-preset`). Either can run under a systemd unit. Because a 40 GB load may take
3–6 min on this rig, health-check timeouts must be raised well beyond llama-swap's 120 s default.
Going headless (`systemctl set-default multi-user.target` or stopping gdm) frees the Xorg context on
all nine GPUs and some host RAM, and is reversible with `set-default graphical.target`.

### Cited Findings
- llama-swap: single binary + one YAML; reads the `model` field of each request and starts the matching `cmd` (with `${PORT}` auto-assigned), replacing the running upstream; one model at a time by default; supports llama-server (best supported), ik-llama-server, vLLM/tabbyAPI via Docker; endpoints `/metrics` (Prometheus, system and GPU), `/running`, `/logs`, `/logs/stream`, `/health`, web UI at `/ui` with playground and token metrics; `hooks` for preload — [llama-swap README, accessed 2026-10-22](https://github.com/mostlygeek/llama-swap).
- llama-swap config keys and defaults: `healthCheckTimeout` 120 s (min 15); `startPort` 5800; `macros`; per model `cmd`, `cmdStop` (default SIGTERM, 5 s before kill), `proxy`, `ttl` (default → `globalTTL` 0 = never unload), `unlisted`, `aliases`, `env` (list of `NAME=value`), `checkEndpoint` (default `/health`), `concurrencyLimit`, `sendLoadingState`, `filters.stripParams/setParams`; `groups.<name>.swap/exclusive/persistent`; alternative `matrix` engine; `hooks.on_startup.preload` — [llama-swap docs/config.example.yaml, accessed 2026-10-22](https://github.com/mostlygeek/llama-swap/blob/main/docs/config.example.yaml).
- llama-server router mode: `--models-dir PATH`, `--models-preset PATH` (INI presets), `--models-max N` (default 4, 0 = unlimited), `--models-autoload`; `/metrics` needs `?model=` in router mode; `GET /health` returns 503 "Loading model" while loading and 200 when ready — [llama-server README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- nvidia-smi persistence mode (`-pm 1`, root, Linux) keeps the driver loaded with no clients, reducing CUDA start-up latency; it resets to Disabled after reboot — [nvidia-smi documentation, accessed 2026-10-22](https://docs.nvidia.com/deploy/nvidia-smi/index.html).
- Headless anecdotes: switching to `multi-user.target` and removing extra services brought one Ubuntu desktop under ~500 MB RAM used (old post, not 24.04) — [fast.ai forums](https://forums.fast.ai/t/how-to-make-desktop-ubuntu-boot-in-headless-mode/19582/6); `systemctl isolate multi-user.target` switches a running system without reboot (reported in the same set of forum results); Xorg's GPU memory use quoted at up to ~400 MB in one older forum post (laptop/PRIME context) — search-result snippets of NVIDIA/forum threads (low quality, **claim to test**).
- Rig fact (measured on the rig): the tested install is an Ubuntu 24.04 desktop install; GNOME and Xorg run at boot and Xorg holds a small context on all nine GPUs; ~1.1 GiB RAM used at idle.

### Inferences
- **llama-swap option:** one group with `swap: true, exclusive: true`; per-model `cmd` pointing at a versioned engine dir (so the same model can be served by several engines as distinct model IDs such as `qwen3-30b-a3b@llamacpp-b8xxx` and `…@ik-<sha>`); `healthCheckTimeout: 900` (loads may take minutes); `ttl` unset (never auto-unload during a benchmark); `env: ["CUDA_VISIBLE_DEVICES=0,1,2,…", "LD_LIBRARY_PATH=/usr/local/cuda-12.9/lib64"]`; `sendLoadingState: true` to see progress in clients. The proxy adds a hop; benchmark against the upstream port directly or verify the proxy adds negligible latency.
- **Router-mode option:** fewer moving parts for llama.cpp-only testing, but it cannot host forks (ik_llama.cpp) or other engines; `--models-max 1` is mandatory here (default 4 would try to keep several 40 GB models resident).
- **Plain systemd option:** one templated unit `llm@.service` with `ExecStart=/opt/engines/%i/run.sh`, `Restart=no` for benchmarking, `MemoryMax=` to protect sshd under 4 GB RAM; switching = `systemctl stop llm@A && systemctl start llm@B`. Simplest for scripted benchmark campaigns where each run is explicit.
- **Swap cost is dominated by load time** (Section 1). Every swap of a 40 GB model costs several minutes; benchmark campaigns should therefore group all tests per model per engine load (llama-bench repeats, perplexity/KLD, API task suites) rather than interleave models.
- **Headless options, all reversible:** (a) temporary `systemctl stop gdm` / `systemctl isolate multi-user.target` (back with `systemctl start gdm` / `isolate graphical.target`); (b) persistent `systemctl set-default multi-user.target` (back with `set-default graphical.target`; takes effect at the next reboot, which on the tested install's passphrase-only LUKS setup requires someone at the keyboard anyway). Keep gdm installed so the console/desktop remains available for local unlock and recovery. Expected gains (claim to test): a few hundred MB host RAM and the Xorg context on each GPU (tens of MB each, matters when packing 6 GB cards to the last layer).
- **Persistence mode** (`nvidia-smi -pm 1`, or the `nvidia-persistenced` service) removes driver init time from "load time" measurements when no X server keeps the driver open — relevant once headless.

- Whether stopping gdm on this board has any side effect on the local console used for LUKS unlock (it shouldn't, since unlock happens in initramfs before gdm, but untested).
- llama-swap's added latency per request (not documented).

## 4. Speed benchmarking methodology

### Takeaway
Use llama-bench for engine-internal throughput (pp/tg at several KV depths, `-r ≥ 5`, JSONL/SQL
output that already records build commit and all settings), llama-batched-bench for concurrency, and
a fixed client against each engine's OpenAI-compatible API for TTFT, end-to-end tok/s and load time.
Log per-GPU power, clocks, temperatures and throttle reasons with `nvidia-smi --query-gpu` at
sub-second intervals and integrate for tokens per joule. Comparability comes from identical model
files (hashes), identical token counts, recorded runtime flags, warm thermal state, and a canary
rerun after every change.

### Cited Findings
- llama-bench: `-p` (default 512), `-n` (default 128), `-pg pp,tg`, `-d/--n-depth` (prefill KV to depth), `-r` (default 5), `--delay` (seconds between tests), `--prio`, `-o/-oe csv|json|jsonl|md|sql`, `--progress`, `--no-warmup` (warmup on by default), `-ngl`, `-ncmoe`, `-sm none|layer|row|tensor`, `-ts`, `-fa on|off|auto`, `-ctk/-ctv`, `-b/-ub`, `-dev`, `-lm` load mode, `-ot` tensor overrides, `-fitt/-fitc` fit-to-memory, `--list-devices`; multiple values via commas or ranges (`first-last+step`, `first-last*mult`); output columns include `build_commit`, `build_number`, `gpu_info`, `backends`, `model_filename`, `model_size`, `model_n_params`, all settings, `n_prompt`, `n_gen`, `n_depth`, `test_time`, `avg_ns`, `stddev_ns`, `avg_ts`, `stddev_ts`; JSON/JSONL add per-repetition `samples_ns`/`samples_ts`; timings exclude tokenization and sampling — [llama-bench README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md).
- `scripts/compare-llama-bench.py` reads SQLite/JSON/JSONL/CSV, compares a baseline (`-b` branch/tag/commit) with a compare commit (`-c`), groups by `-s` properties, prints speedup tables and optional plots (`--plot`, `--plot_x n_depth`); workflow: run llama-bench with `-o sql | sqlite3 llama-bench.sqlite` per build, then compare — [compare-llama-bench.py, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/scripts/compare-llama-bench.py). The scripts dir also has `compare-commits.sh`, `bench-models.sh`, `server-bench.py`, `compare-logprobs.py` — [scripts dir](https://github.com/ggml-org/llama.cpp/tree/master/scripts) (contents not inspected).
- llama-batched-bench: `-npp`, `-ntg`, `-npl` (parallel sequences), `-pps` (shared prompt), `-c`, `-b`, `-ub`, `--output-format jsonl`; columns `T_PP` (time to first token), `S_PP`, `T_TG`, `S_TG`, `S` — [batched-bench README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/batched-bench/README.md).

- nvidia-smi: `--query-gpu=<fields> --format=csv,noheader,nounits -lms <ms>`; queryable power (average, instantaneous, enforced/default/min/max limits), temperature with slowdown/shutdown thresholds, SM/memory clocks, clock event (throttle) reasons, utilization, memory used, PCIe current/max gen and width, pstate; full list via `--help-query-gpu`; **average power over the last second is only supported on Ampere (except GA100) or newer** — on Pascal only the instantaneous sample is available; `nvidia-smi dmon -s pucvmet -d 1 -o T` (p power/temp, u util, c clocks, v violations, m memory, e ECC/PCIe replay, t PCIe throughput); output format is not guaranteed stable — use NVML/pynvml for long-lived scripts — [nvidia-smi documentation, accessed 2026-10-22](https://docs.nvidia.com/deploy/nvidia-smi/index.html).

### Inferences
- **Core llama-bench recipe (option):** `llama-bench -m M -ngl 99 -fa on -p 512 -n 128 -d 0,2048,8192 -r 5 --delay 5 -o jsonl` (plus `-oe md` for humans), one invocation per (engine build, model, flag set); append `-o sql | sqlite3 results.sqlite` to reuse compare-llama-bench.py across commits. Depth sweeps matter for MoE on Pascal because attention cost grows with context while expert matmuls do not.
- **Warmup and steady state:** llama-bench's built-in warmup handles kernel/JIT warmup, not thermals. Options: a 2–3 min throwaway tg run before the real sweep, `--delay` between tests, and logging `temperature.gpu`, `clocks.sm` and clock-event reasons so throttled runs can be flagged or discarded. With 9 cards in one chassis and fixed-speed fans, inner cards may run hotter — log per GPU.
- **Power and tokens/joule:** poll `nvidia-smi --query-gpu=timestamp,index,power.draw,clocks.sm,clocks.mem,temperature.gpu,utilization.gpu,memory.used,pstate,clocks_event_reasons.active --format=csv -lms 200` into a file during each test (or pynvml); integrate power over the test window per GPU, sum across GPUs, divide tokens by joules. Because Pascal gives only instantaneous samples, sample at 100–250 ms. This is GPU-only power; a wall-plug meter is needed for system power (host + fans + PSU losses). Exact field names (`power.draw.instant`, `clocks_event_reasons.active` vs older `clocks_throttle_reasons.active`) must be checked with `--help-query-gpu` on driver 580.
- **Per-GPU utilisation and PCIe:** `nvidia-smi dmon -s pucvt -o T` shows whether pipeline (layer) split leaves most GPUs idle at any instant (expected: ~1/9 busy during tg with layer split) and how much PCIe traffic tensor/row split would generate — useful context for interpreting split-mode results on x1 links.
- **TTFT and end-to-end speed (engine-agnostic):** a small Python client that streams `/v1/chat/completions` with fixed prompts (e.g. 512, 4k, 16k prompt tokens measured with the model's tokenizer), `temperature=0`, fixed `max_tokens`, `cache_prompt=false` (or a unique prefix per request) to defeat prompt caching, records time-to-first-byte, time-to-first-content-token, total time and server `timings`. Run 5 repeats, report median and spread. llama.cpp's `scripts/server-bench.py` may already do this (not inspected).
- **Load time:** measure from process start to first 200 on `/health` (503 while loading), plus llama.cpp's own load log lines, for each storage source and load mode; drop page cache (`sync; echo 3 > /proc/sys/vm/drop_caches`) before cold-load runs and say whether runs are cold or warm. With 4 GB RAM most loads are effectively cold anyway.
- **Making engines comparable:** same GGUF (hash) where the fork can load it; same context size, KV-cache type, FA on/off, batch/ubatch, split mode and GPU set; same prompt token counts; record every engine default that differs (ik_llama.cpp's defaults and flag names differ from mainline). Prefer each engine's own llama-bench for pp/tg (both mainline and ik have one) plus the shared API client for TTFT so at least one measurement is identical across engines. Report mean ± stddev and the number of repetitions; treat differences inside ~2 × stddev as noise.
- **Canary run after every change:** one small MoE that fits on 2–3 GPUs (fast to load) plus one large model spanning all 9, fixed flags, fixed llama-bench command; flag a change when canary tg/pp moves beyond its historical spread.

## 5. Quality benchmarking methodology (cheap enough per model/quant)

### Takeaway
Tiered options from cheapest to costliest: (1) perplexity on a fixed text with fixed context and
chunks (within one model family only); (2) KL-divergence against reference logits generated on the
workstation from a higher-precision quant — the most sensitive cheap signal for "how much did this
quant/engine change the model", but the logits file is large (≈ scored tokens × vocab × 2 bytes) so
chunk counts must be limited; (3) small task subsets over the OpenAI-compatible API (tool-call smoke
tests, IFEval/GSM8K/HumanEval+/MBPP+ subsets, an Aider polyglot slice). Subset results need error
bars: at n=100 a 70 % score has ±9 pp 95 % CI, so small task suites only detect large regressions
unless comparisons are paired.

### Cited Findings
- Perplexity convention: Wikitext-2 test (`scripts/get-wikitext-2.sh`); perplexity is not directly comparable between models, especially with different tokenizers — [perplexity README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md). Qwen's docs show `llama-perplexity -m … -f wiki.test.raw -ngl 80` and say it is mainly for comparisons — [Qwen docs: llama.cpp quantization](https://qwen.readthedocs.io/en/stable/quantization/llama.cpp.html). Quant publishers report wiki.test.raw PPL against BF16/Q8_0 baselines (e.g. GLM-4.5-Air BF16 4.5704, Q8_0 4.5798, IQ5_K 4.5867) — [ubergarm GLM-4.5-Air-GGUF card](https://huggingface.co/ubergarm/GLM-4.5-Air-GGUF).
- KL-divergence workflow: run `llama-perplexity` on the reference model with `--kl-divergence-base file.kld` to save logits; then run the quant with `--kl-divergence-base file.kld --kl-divergence`. Logits are stored as scaled 16-bit integers; files are large (~11 GiB for LLaMA 2, ~37 GiB for LLaMA 3 on Wikitext-2). Printed stats: mean KLD ± uncertainty, PPL ratio and log ratio, PPL difference, mean Δp of the correct token, Pearson correlation, Δp percentiles, RMS Δp, "same top p" (top-token agreement); a BF16-vs-FP16 table shows 99.9 %/99 % KLD percentiles. - Unsloth argues "using perplexity is incorrect since output token values can cancel out, so we must use KLD or harder benchmarks like Aider"; Dynamic 3.0 adds "Divergence-300 @32" (300 held-out prompts from Terminal-Bench 2.1, DeepSWE, Harbor, MathArena 2025-26, non-Latin/long-document; greedy 32 tokens vs BF16) and reports KLD on unseen Wikitext and code; context length not stated; results self-reported — [Unsloth Dynamic 3.0 GGUFs docs, accessed 2026-10-22, newest dated note 2026-04-20](https://unsloth.ai/docs/basics/dynamic-3.0-ggufs). ### Inferences
- **Binomial error bars (arithmetic):** SE = √(p(1−p)/n). At p ≈ 0.7: n=50 → ±6.5 pp SE (±12.7 pp 95 % CI); n=100 → ±4.6 (±9.0); n=250 → ±2.9 (±5.7); n=500 → ±2.0 (±4.0); n=1319 → ±1.3 (±2.5). Quant-to-quant differences are often a few pp, so unpaired 100-item subsets can only flag gross breakage (e.g. broken chat template, tool-call parser failures, collapsed low-bit quants). Paired analysis on identical items, plus fixed item IDs across every run, is the cheapest way to tighten comparisons.
- **KLD is the high-signal, low-cost option for quant/engine comparisons within one model:** every scored token contributes, so ~25–50k tokens gives tight uncertainty (the tool prints ±). It answers "how far is this quant/engine from the reference", not "is the model good".
- **KLD logistics on this rig (estimates):** the stored size is ≈ scored tokens × n_vocab × 2 bytes; llama-perplexity scores the second half of each context window (consistent with the README's 37 GiB for LLaMA 3: ~150k scored tokens × 128k vocab × 2 B). For a ~152k-vocab model at `-c 512`, each chunk ≈ 256 × 152k × 2 B ≈ 78 MB → 100 chunks ≈ 7.8 GB, 50 chunks ≈ 3.9 GB; ~200k-vocab models are ~30 % larger. Options: limit `--chunks` (50–100), keep `.kld` files on the workstation and read them over NFS (one sequential pass), or delete after use. Context and chunk settings must be identical between base and comparison runs.
- **Reference logits on the workstation (options):** BF16 or Q8_0 of the same model if it fits in the workstation's RAM plus VRAM (e.g. a ~30B-A3B MoE at Q8_0 ≈ 32 GB fits on a workstation with enough RAM to hold a Q8_0 of a ≤36B MoE, 32–38 GB); for 100B-class MoEs a Q8_0 exceeds the RAM of a typical workstation, so either mmap-from-NVMe (slow but one-off for 50 chunks) or use the best available quant as the reference and state it. Also possible: compute the quant's KLD on the workstation instead of the rig (faster) — but that measures the workstation's kernels; running on the rig captures Pascal kernel numerics (MMQ/dp4a, FA, KV-cache quant) and engine differences. Sanity-check vocab and tokenizer identity between reference and test models.
- **Task-suite run-time estimates at 20–50 tok/s (all claims to test; prompt-processing speed on the rig unknown):**
  - tool_bench.py (2 tests × n=10 × 3 temps ≈ 60 short calls): ~5–15 min.
  - IFEval subset 150 of 541 (~200–400 output tokens, short prompts): ~150 × ~10 s ≈ 25–40 min non-reasoning; full 541 ≈ 1.5–2.5 h.
  - GSM8K subset 250 (zero-shot CoT ~150–300 output tokens; 8-shot adds ~1k prompt tokens each): ~45–90 min; full 1,319 ≈ 4–8 h.
  - HumanEval+ 164 (~150–400 output tokens): ~30–60 min generation + fast sandboxed execution on the workstation; MBPP+ 378 ≈ 1–2 h.
  - Aider polyglot full 225 × up to 2 tries with multi-k-token prompts and outputs: likely many hours to a day at these speeds; a fixed slice of 30–50 exercises (same `--keywords`/IDs every time) ≈ 2–5 h.
  - Reasoning ("thinking") models multiply generation by ~5–20× (1–4k thinking tokens per item); options: disable thinking where the model supports it, cap `max_tokens` (and report the cap), or test only on the smallest subsets.
- **Where to run the harnesses:** on the workstation, pointed at the rig's server over LAN, so the rig's 2 cores and 4 GB RAM only serve tokens and code execution sandboxes run on the workstation (Docker).
- **Chat template correctness is a quality variable:** llama-server defaults `--jinja` on; engines/forks may parse tool calls and reasoning differently (`--reasoning-format`), which shows up as task-suite failures unrelated to quantization — tool_bench.py and IFEval catch this cheaply.
- **Determinism:** use `temperature=0`/greedy, fixed seed, `cache_prompt=false` for quality runs (the server README warns logits can differ across batch sizes with prompt caching), `-np 1`.

### Gaps
- Optimal chunk count/context for KLD on MoE models (no source gives a rule; the printed ± is the practical guide).
- No source on LiveCodeBench subset tooling for local endpoints, or official current problem counts.
- No measured prompt-processing speeds on this rig, so all task-suite durations are rough.
- Whether lm-eval's `local-completions` works against ik_llama.cpp's server for loglikelihood tasks (needs `/v1/completions` with `logprobs`/`echo` support) — untested.

## 6. Experiment tracking: results schema and a baseline protocol

### Takeaway
llama-bench's own JSONL/SQL rows already capture build commit, model file, and all runtime settings,
so the simplest robust option is a SQLite database (or JSONL files in git) where llama-bench rows are
stored as-is and a second table records everything llama-bench does not know: engine fork, build
flags, model file hash, storage source, load time, TTFT, power/energy, thermals, quality metrics and
host state. A fixed canary protocol rerun after every change makes cross-experiment results trustworthy.

### Cited Findings
- llama-bench output fields (build_commit, build_number, cpu_info, gpu_info, backends, model_filename, model_type, model_size, model_n_params, n_batch, n_ubatch, n_threads, type_k, type_v, n_gpu_layers, n_cpu_moe, split_mode, main_gpu, flash_attn, devices, tensor_split, tensor_buft_overrides, use_mmap, use_direct_io, n_prompt, n_gen, n_depth, test_time, avg_ts, stddev_ts, samples_ts) — [llama-bench README, accessed 2026-10-22](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md).
- compare-llama-bench.py consumes the SQLite produced by `llama-bench -o sql` and compares commits — [compare-llama-bench.py](https://github.com/ggml-org/llama.cpp/blob/master/scripts/compare-llama-bench.py).
- Aider recommends committing the harness repo before a run so the recorded `commit_hash` is clean — [Aider benchmark README](https://github.com/Aider-AI/aider/blob/main/benchmark/README.md); EvalPlus scores shift with dataset version (MBPP+ v0.2.0) — [EvalPlus README](https://github.com/evalplus/evalplus). Both argue for recording harness and dataset versions.
- nvidia-smi output is not guaranteed stable across drivers; NVML is preferred for long-lived scripts — [nvidia-smi docs](https://docs.nvidia.com/deploy/nvidia-smi/index.html).

### Inferences
- **Proposed `runs` record (one row per measurement; JSON or SQLite columns):**
  - Identity: `run_id`, `timestamp_utc`, `campaign`, `operator`, `notes`.
  - Engine: `engine` (llama.cpp / ik_llama.cpp / other), `engine_commit`, `engine_build_number`, `build_host` (rig / workstation-docker), `container_image_digest`, `cuda_version`, `cmake_flags` (full string or hash + file), `binary_path`.
  - Host state: `driver_version`, `kernel`, `headless` (bool), `persistence_mode`, `free_ram_before_mb`, `page_cache_dropped` (bool), `ram_total_gb` (records the RAM upgrade), `power_limit_w` per GPU.
  - Model: `model_repo`, `model_file`, `quant`, `file_size_bytes`, `file_sha256` (or xxh128), `imatrix_source`, `n_params_total`, `n_params_active`, `storage_source` (local-ssd / usb-ssd / nfs / nbd), `load_mode` (mmap / none / dio).
  - Placement: `gpu_set` (CUDA_VISIBLE_DEVICES), `split_mode`, `tensor_split`, `n_gpu_layers`, `override_tensor`, `ctx_size`, `type_k`, `type_v`, `flash_attn`, `batch`, `ubatch`, `parallel`.
  - Speed: `load_time_s` (process start → /health 200), `pp_tps` (with `n_prompt`, `n_depth`), `tg_tps` (with `n_gen`, `n_depth`), `stddev`, `repetitions`, `ttft_ms` (prompt length), `e2e_tps`, `batched` results.
  - Resources: `vram_used_mb_per_gpu` (array of 9), `host_rss_mb_peak`, `gpu_temp_max_c`, `throttle_events`, `energy_j_gpu`, `avg_power_w_gpu`, `tokens_per_joule`.
  - Quality: `ppl` (+ dataset, ctx, chunks), `kld_mean`, `kld_p99`, `same_top_p`, `kld_ref` (which reference file), task scores with `n_items`, `item_ids_hash`, `harness_version`, `dataset_version`, `max_tokens`, `thinking_enabled`.
  - Raw artefacts: paths to llama-bench JSONL, nvidia-smi CSV, server logs.
- **Storage options:** (a) SQLite `results.sqlite` with a `llama_bench` table (raw rows) + `runs` table; (b) append-only JSONL per campaign committed to version control (diffable, simple); (c) both. Raw nvidia-smi/power logs probably belong outside git (size), referenced by path + hash.
- **File hashing cost:** hash once on the workstation at download time and store in the manifest; the rig only verifies via rsync's transfer checksum or a size + partial-hash check, to avoid hashing 40 GB on the Celeron before every run.

### Gaps
- No standard community schema for multi-engine local-LLM results was found; the above is a synthesis.

## 7. Experiment ideas and baseline-protocol options

### Takeaway
The highest-value early experiments are infrastructure ones that decide the workflow for every later
model: where models are read from (local vs NFS vs USB, and which load mode), whether
workstation-built binaries match rig-built ones, how much headless mode frees, and whether load is
really PCIe-bound. A small, fixed baseline protocol (canary models, fixed llama-bench + KLD +
tool-call smoke test) rerun after each change keeps all later results comparable. Everything below is
framed as options.

### Cited Findings
- Load modes and their documented trade-offs (`auto`/mmap default, `none`, `dio`; dio pathological on network shares; repeat-load caching only when RAM suffices) — [llama-bench README](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md); [discussion #18758](https://github.com/ggml-org/llama.cpp/discussions/18758).
- Loader uploads sequentially with 4 × 1 MiB staging buffers in the non-mmap path — [llama-model-loader.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model-loader.cpp).
- Wrong-architecture builds silently run slower via PTX JIT — [Ian Paterson 2026](https://ianlpaterson.com/blog/llama-cpp-build-from-source-cuda-benchmark/).
- Pascal MMQ tile config may leave ~12 % pp on the table (issue title) — [llama.cpp #30235](https://github.com/ggml-org/llama.cpp/issues/30235).
- Rig: one-GPU-at-a-time host→GPU ~189 MB/s vs ~715 MB/s with all nine in parallel — [hardware spec](../../mining_rig.md).

### Inferences

**Infrastructure experiments (options)**
1. **Load time by storage source × load mode.** Same model (e.g. a ~20 GB MoE that fits on local disk) loaded from local SSD (LUKS), NFS (ro, rsize 1 MiB, tuned read-ahead), USB 3.0 SSD (UAS confirmed), and, if set up, NBD; each with `-lm mmap`, `-lm none`, `-lm dio`; cold cache; 3 repeats; record wall time to /health 200, host RSS peak, and `dmon -s t` PCIe throughput. Tests the claim that load is capped at ~190 MB/s by sequential single-GPU uploads.
2. **Is load PCIe-bound or storage-bound?** Same model from tmpfs/page cache (only possible for small models with 4 GB RAM, or after a RAM upgrade) vs SSD: if times match, storage is not the limit.
3. **LUKS / CPU crypto ceiling.** `cryptsetup benchmark`, `openssl speed -evp aes-128-gcm`, `dd`/`fio` read of a large file through dm-crypt vs raw USB SSD; check `/proc/cpuinfo` for `aes`.
4. **Transfer method throughput.** 10 GB file: rsync over SSH (default cipher), rsync with `aes128-gcm`/`chacha20` and `Compression=no`, rsync daemon, NFS `cp`, `hf download` directly on the rig vs on the workstation; record MB/s and rig CPU usage.
5. **Network FS behaviour with llama.cpp.** Does mmap over NFS/SMB/SSHFS load correctly; any SIGBUS or "failed to mmap"; inference speed identical after load (it should be, since weights live in VRAM)?
6. **Headless vs desktop.** `free -m`, `nvidia-smi --query-gpu=memory.used` per GPU, and max loadable context/layers, with gdm running vs stopped; plus whether persistence mode changes CUDA init time.
7. **Workstation-built vs rig-built binary parity.** Same commit; identical greedy output for a fixed prompt; llama-bench pp512/tg128 at d=0 and d=8192 within noise; `ldd`/`objdump` checks for AVX instructions and GLIBC symbol versions; startup log shows `ARCHS = 610`.
8. **Dynamic vs static build.** Size on disk, start-up time, and speed parity.
9. **Build-flag variants.** `FORCE_MMQ` on/off, `CUDA_GRAPHS` on/off, `FA_QUANTS=all` (enables q8_0/q4_0 KV mixes), on 2–3 models; plus any Pascal MMQ tuning patch (issue #30235) as a separate build.
10. **Thermal steady state.** 30-minute continuous tg run; per-GPU temperature, SM clock and throttle reasons over time; tok/s at minute 1 vs minute 30; inner vs outer slot cards; effect of 60 W vs 75 W power limits on tokens/joule (power-limit changes alter the rig's state and warrant a deliberate decision).
11. **Power measurement validity.** Compare sampling at 100 ms vs 1 s; sum of GPU power vs a wall-plug meter reading.
12. **RAM upgrade before/after** (if bought): repeat experiments 1, 2, 6 with 20–36 GB RAM; also whether more RAM enables useful `-ncmoe` CPU offload on SSE-only cores (expected: very slow).
13. **Swap overhead.** Time to switch models via llama-swap vs systemd vs router mode, for small and large models; proxy latency vs direct upstream.

**Quality/methodology experiments (options)**
14. **KLD stability vs chunk count.** For one model, KLD with 25/50/100/200 chunks; pick the smallest count whose ± is well below differences of interest.
15. **Rig vs workstation KLD for the same quant** (engine/kernel numerics on Pascal vs the workstation's newer CPU and GPU).
16. **Engine numerics.** Same GGUF on llama.cpp vs ik_llama.cpp: KLD vs the same reference, plus greedy-output identity rate on a fixed prompt set.
17. **Subset sensitivity.** For one model pair (e.g. Q4 vs Q3 of the same MoE), check whether a 100-item paired IFEval/GSM8K subset reproduces the ranking from the full set.

**Baseline protocol options (rerun after every engine/build/driver/host change)**
- **Option A — minimal canary (~20–30 min incl. load):** one small MoE on a fixed 2–3 GPU subset: `llama-bench -p 512 -n 128 -d 0,4096 -r 5 -fa on -o jsonl` + `tool_bench.py run --n 10 --temp 0` + KLD on 25 chunks against a stored reference. Accept the change if pp/tg are within the canary's historical ± 2σ, KLD unchanged within its ±, tool-call success unchanged.
- **Option B — full-rig canary (~1 h):** Option A plus one large model spanning all nine GPUs (load time from the chosen storage source, pp/tg at d=0/8192, TTFT at 512/4k prompt via the API client, power log → tokens/joule).
- **Option C — per-new-model protocol:** Option B's speed suite + KLD (50–100 chunks vs workstation Q8_0/BF16 reference) + tool_bench + fixed paired subsets (e.g. IFEval 150, GSM8K 250, HumanEval+ 164) with frozen item IDs; Aider polyglot slice only for shortlisted models.
- **Common rules for any option:** same canary GGUF files (hash-pinned) forever; same prompts/item IDs; record host state (headless, persistence, RAM, page cache dropped); warm-up run discarded; per-GPU temps logged; results written to the schema in Section 6 before any interpretation.

### Gaps
- All durations above are estimates pending first measurements on the rig.
- No external reference exists for what "normal" run-to-run variance looks like on this rig; the first week of canary runs would establish it.
